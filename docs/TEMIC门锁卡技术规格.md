# TEMIC 智能门锁卡 技术规格

> 对象：`D:\Program Files\智能门锁管理软件`（AppVer=LOCK_V8，LockSoftVer=V8.9，LockVer=V8）
> 卡型：125 kHz TEMIC（T5557/T5567 类），7 页 × 4 字节
> 读卡器：CH340 USB 转串口 + LC 系列发卡器
> 文档状态：**交付版**。标注约定：**【实测】**=有抓包/联机证据；**【推断】**=由证据归纳但未穷尽；**【待定】**=机制未证实。

---

## 1. 结论摘要

1. 本软件的 TEMIC 卡**不是**用驱动里的 `tem_*_sdk` 写的。原软件只用驱动的**底层页读写**（`te_read` / `te_setuppwm` / `te_writepwm`），卡内是**8 字节明文**私有格式。
2. 驱动 `LC32RFRW.dll` 确实提供一套"原厂 SDK"（`tem_writedoorcard_sdk` / `tem_writetimercard_sdk` 等），但它写的是 **16 字节加密格式（4 页，含 `"GUEST"` 明文标记）**，且**要求卡上已有合法的 16 字节记录**；对空白卡直接返回 `4`（卡数据校验失败）。**本产品线不适用**。
3. 卡内格式已完整解出，任意房号 / 任意天数 / 任意小时 / 总控 / 管理卡都能逐字节复刻，**实测可开门**。
4. 关键前提：写卡必须用 `config_parameter(0)`（不加扰码）；写密码为 `12000206`；写完立即回读会读到旧值，需重新打开或等待。

## 2. 系统架构

```
NacreHis.exe                     门锁软件主程序（MFC）
  └─ SmartLock.dll               门锁业务模块（唯一导出 DoSmartLockDlg）
       └─ SM_RW_Card.dll         读写卡引擎（12 个 Do* 导出，动态 LoadLibrary 加载驱动）
            └─ LC32RFRW.dll      读卡器驱动（92 个导出，含 tem_*_sdk 高层函数）
                 └─ CH340 串口 → 发卡器 → TEMIC 卡
```

- `LC32RFRW.dll` 在 `IOServer\LC2000\` 与 `IOServer\LC2008\` 下**是同一个文件**（SHA-256 `f2f483e0…`）。
- 驱动导出分两类：
  - **底层**：`mif_*`（Mifare）、`tm_*`（Temic 1557）、`te_*`（T5557/5567）、`em4305_*`、`config_parameter`、`Cal_Crc8`、`get_id_asc`、`read/write_inside_ram` 等；
  - **高层**：`tem_readdoorcard_sdk`、`tem_writedoorcard_sdk`、`tem_readtimercard_sdk`、`tem_writetimercard_sdk`、`tem_readlcdoorcard_sdk`、`tem_writelcdoorcard_sdk` 等。
- 原软件实际走的是**底层**，所以第三方只要复刻 8 字节格式即可，**不需要也无法使用**高层 SDK。
- 每一层具体调用了哪些接口（含 `SM_RW_Card.DoWriteCard` 的卡型分派、TEMIC 写入实现
  `sub_10011DEB`、驱动函数表偏移、密码 `12000206` 的来源），见独立文档
  **`发卡调用链逆向.md`**。

## 3. 串口协议

> 帧层与 `te_*`（T5557/5567）函数的逐个逆向（含扰码算法、配置字位域、应答状态码）
> 见独立文档 **`T5557-5567函数逆向.md`**。本节只给结论性摘要。

### 3.1 帧格式

```
80 <cmd> <payload...> <cs>
长度 = 3 + payload 字节数
cs = 0xFF - (0x80 + cmd + Σpayload) & 0xFF
```

### 3.2 扰码开关（关键坑）

`config_parameter(N)`：

| N | 行为 |
|---|---|
| **0** | **明文**（原软件使用） |
| 3 | 载荷按 256 字节换码表加扰（`sub_1000100C`，逆函数 `sub_100010E7`） |

同一写命令在 `N=0` 时是 `01DEADBEEF`，在 `N=3` 时是 `7B87192903`。**用错会导致"能读不能写"**。

### 3.3 常用命令

| cmd | 名称 | 说明 |
|---|---|---|
| 0x00 | config_parameter | 见上 |
| 0x02 | mif_selecard | 卡型：3/4/5/6/255 有效；**5 = TEMIC** |
| 0x05 | mif_shake | 握手；首次常返回 2，需 `config_parameter` 后重试 |
| 0x0E | mif_beep | 蜂鸣 |
| 0x15 | te_read | 读 28 字节，返回 58 个 HEX 字符 |
| 0x16 | te_write | 写单页（无密码） |
| 0x17 | te_writepwm / te_setuppwm | 带密码写页 / 设置写密码 |

### 3.4 写卡时序（实测）

```
mif_selecom(port, 9600)
mif_shake()                       // 可能返回 2
config_parameter(0)
mif_shake()
mif_selecard(5)
te_read_asc(buf)                  // 读一次，判断卡状态
te_setuppwm(a1=0, a2=2, a3=0, a4=1, pwd="12000206")
te_writepwm(a1=0, page=1, pwd="12000206", data=P1)
te_writepwm(a1=0, page=2, pwd="12000206", data=P2)
mif_beep(2)
```

- `te_write`(0x16) 对空白卡**不可用**，必须走 `setuppwm + writepwm`。
- 写完**立刻回读会读到旧值**，须重新打开串口或等待约 1 秒后再读。
- 原软件对每个操作会 `FreeLibrary` 驱动，因此挂钩调试时会出现"补丁被卸载"的现象。

## 4. 卡内数据结构（前 2 页 8 字节 + 页3/页4 的隐藏字段）

```
页1:  5B  EC  [B2]  [B3]
页2:  [D0] [N_L] [N_H] [B7]
页3:  00 00 00 00    ← 实测：承载「开反锁」等字段，但 T5557 卡写不进去（见 4.5）
页4:  00 00 00 00    ← 实测：承载「退房钟点」，同样写不进去
页5~7: 00 00 00 00
```

> **2026-11-08 重要修正**：页2 第 4 字节**不是固定后缀 `AB`**，而是「年份 + 月日」字段（见 4.4）；
> 页3/页4 也不是「未使用」，原厂 SDK 会在里面存退房钟点与开反锁（见 4.5）。

| 字节 | 源码构造式（`CardBuilder.BuildGuest`） | 含义 |
|---|---|---|
| `5B` `EC` | `Prefix0` / `Prefix1` | 固定前缀 |
| **`B2`** | `((序号 & 0x0F) << 4) \| low` | 高 4 位 = 序号低 4 位；低 4 位 = `low`（见 4.1） |
| **`B3`** | `(序号 >> 4) & 0xFF` | 序号高 8 位；客卡通常 `00`，总控卡 `FF` |
| **`D0`** | `DurationDays(days)` / `DurationHours()` | 时长码（见 4.2） |
| **`N_L`** | `cardNo & 0xFF` | 卡号低字节（⚠️ 若按另一种切分，其 bit5 = 开反锁，见 4.5） |
| **`N_H`** | `(cardNo >> 8) & 0xFF` | 卡号高字节（卡号 = `N_H << 8 \| N_L`） |
| **`B7`** | 源码里叫 `Suffix = 0xAB` | ⚠️ **实为「年份 + 月日」字段**（见 4.4），安装卡除外（见 5.3） |

### 4.1 低 4 位标志

| 卡类型 | 规则 | 样本 |
|---|---|---|
| 日租卡 | `(天数 & 3) == 1 ? 1 : 0` | 1天→1、2天→0、3天→0、4天→0、5天→1 |
| 钟点卡 | 恒为 `1` | 1h/3h/6h/62h 全部为 1 |

> 14 个样本全部命中；`--low N` 可手动覆盖。

### 4.2 时长码 `D0`

| 卡类型 | 编码 | 样本 |
|---|---|---|
| 日租卡 | `0x80 ｜ 天数` | 1天→`81`、2天→`82`、5天→`85` |
| 钟点卡 | `0x40 ｜ (小时 + 1)` | 1h→`42`、3h→`44`、6h→`47`、62h→`7F` |
| **长期日租（>63 天）** | **`0xC0 ｜ 月数`**（1 月 ≈ 31 天） | 90天→`C3`、120→`C4`、360→`CC`、1095→`E3` |

- 小时数有效范围：客卡 1~62（`0x40|63 = 0x7F` 为上限），总控卡 1~63。
- 天数有效范围：1~63 走 `0x80` 段；64 天以上走 `0xC0` 段（月数编码）。
- 高 2 位即"单位"：`0x40` = 小时、`0x80` = 天、`0xC0` = 月。

**月数编码的换算（实测 6 组全部吻合）**：

| 设定天数 | 字节 | 低6位 | 天数/31 |
|---|---|---|---|
| 90 | `C3` | 3 | 2.90 |
| 120 | `C4` | 4 | 3.87 |
| 150 | `C5` | 5 | 4.84 |
| 360 | `CC` | 12 | 11.61 |
| 390 | `CD` | 13 | 12.58 |
| 1095 | `E3` | 35 | 35.32 |

即 `月数 = round(天数 / 31)`。**注意用 30 天算会对不上**（1095/30 = 36.5）。

**2026-11-08 实测修正（TD-145）：低 6 位是「月数」，锁按月历加法算，不是按天数近似。**

用原厂 SDK 按「时间单位 = **4（月）**、时间长度 = **4**」写卡，卡内得到 `0xC4`，
`RWCardDemo` 算出的结束时间是 **2027-03-04 12:00**（起始 2026-11-04 16:00）—— **正好 +4 个日历月**，
不是「4 × 31 = 124 天」（那样会到 2027-03-08）。

| 我们发卡台送什么 | `DurationDays()` 写入 | 锁实际按什么算 |
|---|---|---|
| 90 天 | `0xC0 \| round(90/31) = 0xC3` | **3 个日历月**（11-04 → **02-04**，共 **92 天**） |
| 120 天 | `0xC4` | **4 个日历月**（11-04 → 03-04，共 120 天）|
| 1095 天 | `0xE3`（35 月） | **35 个日历月**（≈ 1065 天，**比 1095 少约 30 天**）|

**结论**：90/150/180/210/240 这类「非整月档位」会被锁按整月执行，**与设定天数有 ±2~3 天偏差**；
1095 天档位的偏差最大（约一个月）。详见 TD-145。

⚠️ **软件界面限制**：超过 63 天无法手动输入，只能选固定档位（90 / 120 / 150 / 180 / 210 / 240 … / 1095）。

⚠️ **1095 天（3 年）的卡刷一次会把该房间的有效卡顶到 3 年后**，之后正常卡全失效，需刷复位卡恢复 —— 测试时别拿它刷门。

### 4.3 卡号

- 16 位，低字节在前。
- 现象：卡号小于锁内已见最大值时被拒（详见第 6 节，**结论待定**）。

### 4.4 破译过程：页2 第 4 字节（`Suffix = 0xAB`）到底是什么【历史记录】

> **最终结论见 §4.4.2**。本节保留推导过程（含两次推翻），供日后复查证据链。

**最初判断（错误）**：以为 `AB` 是「年份 + 月日」字段，因为改它会改变 RWCardDemo 显示的年份。

**实测反证**（三张卡对照）：

| 卡 | 页1 | 页2（卡号） | RWCardDemo 读出日期 |
|---|---|---|---|
| 我们的 220 卡 | `5BECF100` | `810624` **`AB`**（卡号 `0x2406`） | 11-04 |
| SDK 写的 220 卡 | `5BECF000` | `818143` **`AB`**（卡号 `0x4381`） | **11-08** |
| 只改页1 的对照卡 | `5BECF100` | `818143` **`AB`**（卡号 `0x4381`） | **11-08** |

**三张卡 `AB` 完全相同，日期却不同** → `AB` 不是日期字段。

**真实机制**【反编译 `tem_readdatetime13_sdk`】：日期是从 **卡号（`BYTE5`/`BYTE6`）+ `AB`（`BYTE7`）** 一起位运算解码出来的：

```c
v8      = sub_1000260C(BYTE7 >> 4);                            // 从 BYTE7 高 4 位查表
BYTE1   = (BYTE7 & 0xF) % 10 + 16 * ((BYTE7 & 0xF) / 10);       // BYTE7 低 4 位
BYTE2   = ((int)BYTE6 >> 3) % 10 + 16 * (...);                  // BYTE6（卡号高）
BYTE3   = ((BYTE5 >> 6) + ((4 * BYTE6) & 0x1C)) ...             // BYTE5（卡号低）
```

**为什么原厂能解出真实日期**：原厂的「卡号」实际是**作业流水号 = 年月日时 + 小时内序号**（如 `2611081401`），
卡号本身就编码了发卡时间，所以解码出来是对的。

**我们的情况**：卡号是纯递增计数器（`0x2406`、`0x4381`），解码出的日期是**假日期**（恒显示 11-04 一类值）。

**影响**：

| 项 | 影响 |
|---|---|
| 开门 | ❌ 无影响（锁只比较卡号大小） |
| 界面/读卡器显示的发卡时间 | ⚠️ 是假的（实际是卡号的函数） |
| 酒店追溯「这张卡什么时候发的」 | ❌ 做不到 |

**要根治**：必须让**卡号带时间戳**（TD-147 的真实内容），而不是改 `AB`。`AB` 保持 `0xAB` 即可。

#### 4.4.1 中间推导（两组对照样本）【历史记录，结论见 4.4.2】

```
5BEC0100 8181 23 8B  →  RWCardDemo 读：24110414  (2024-11-04 14点)
5BEC0100 8181 23 AB  →  RWCardDemo 读：26110414  (2026-11-04 14点)
                    ↑↑ ↑↑
              卡号相同（0x2381），只有页2[3] 从 8B 变 AB
```

| 字段 | 卡内来源 | 验证 |
|---|---|---|
| **年** | `页2[3]` **高 4 位**，按 16 年段还原 | `年 = 2000 + 16×⌊(当前年−2000)/16⌋ + 高4位`；当前段下即 `+2016` |
| **月** | `页2[3]` **低 4 位**（BCD） | `0xB`=11 → 11 月 ✅ |
| **日** | **卡号高字节 `>> 3`** | `0x23`>>3=**4**→04；`0x43`>>3=**8**→08 ✅ |
| **时** | 卡号低字节（两条样本都是 14 点，尚未区分） | 【待定】 |

**对照三张真实卡**：

| 卡 | `页2[3]` | 卡号 | 解出 | demo 显示 |
|---|---|---|---|---|
| 旧电脑原厂软件发的（201） | `AB` | `0x4381` | 2026-11-**08** | **11-08** ✅ |
| 我们用 SDK 写的（220） | `AB` | `0x4381` | 2026-11-**08** | **11-08** ✅ |
| 我们发卡台发的（220） | `AB` | `0x2406` | 2026-11-**04** | **11-04** ❌ |

**结论**：年月在两边都是 `AB`（2026-11，写死）；**唯一差异是卡号高字节的 bit3..7 编码了「日」**。

**修复方向（TD-147）**：把 `CardNo.state` 从「纯递增计数器」改成「时间编码」——

```
卡号高字节 bit3..7 = 发卡「日」（0..31）
卡号低字节        = 发卡「时」+ 小时内序号
```

「日 + 时」随时间自然递增，只要同小时内序号也递增，就同时满足**锁的水位单调性**和**日期可还原**两个要求。

#### 4.4.2 最终结论：卡号就是紧凑时间戳（6 组样本全部验证）

**卡内没有独立的「发卡日期」字段**，时间完全由 **卡号（2 字节）+ 页2[3]** 共同编码：

| 字段 | 位置 | 编码 |
|---|---|---|
| **年** | `页2[3]` 高 4 位 | `年 = 2000 + 16×⌊(当前年−2000)/16⌋ + 高4位`（16 年一循环；当前段 2016–2031 等价于「+2016」） |
| **月** | `页2[3]` 低 4 位 | BCD |
| **日** | 卡号**高字节** bit3–7 | 0–31 |
| **时** | 卡号**高字节** bit0–2（×4）+ 卡号**低字节** bit6–7 | 0–23 |
| **小时内序号** | 卡号**低字节** bit0–5 | 0–63 |
| **挂失** | `页1[2]` 低 4 位 | 0 = 非挂失、1 = 挂失 |

即：**卡号 16 位 = 日(5) + 时(5) + 小时内序号(6)** —— 与文档「作业流水号 = 年月日时 + 小时内序号」完全对应。

**6 组实测样本**（`RWCardDemo` 读数为准）：

| 卡字节 | 卡号 | 页2[3] | 页1[2] | 解出 | demo 读数 |
|---|---|---|---|---|---|
| `5BEC0100 8181238B` | `0x2381` | `8B` | `01` | 2024-11-04 14:01 | 24110414 ✅ |
| `5BEC0100 818123AB` | `0x2381` | `AB` | `01` | 2026-11-04 14:01 | 26110414 ✅ |
| `5BEC0100 810123AB` | `0x2301` | `AB` | `01` | 2026-11-04 12:01 | 26110412 ✅ |
| `5BEC0100 81015BAA` | `0x5B01` | `AA` | `01` | 2026-10-11 12:01 | 26101112 ✅ |
| `5BEC0000 81345BAA` | `0x345B` | `AA` | `00` | 2026-10-11 12:52 | 26101112 ✅ |
| `5BEC0000 81345AAA` | `0x345A` | `AA` | `00` | 2026-10-11 08:52 | 26101108 ✅ |

**数据来源**：用户用原厂 SDK（`tem_writedoorcard13_sdk`，经 patch 关扰码后）按指定 `fksj` / 序号 / 挂失参数逐张写卡，
再用 `RWCardDemo.exe` 读回核对。

**对我们的影响**：`CardNo.state` 是**纯递增计数器**（`0x2406`、`0x2B92`…），
按上面的规则解出来是「日 4 / 时 12 / 序号 6」这类**假时间**，所以读卡器永远显示 2026-11-04。
改造方案见 TD-150。

**遗留**：`页1[2]` 高 4 位（`B2` 的 `0x0/0x1/0xF`）语义仍未完全确定，
目前只确认了**低 4 位 = 挂失**；高 4 位是房间序号的一部分（`(序号 & 0x0F) << 4`），
但总控卡/复位卡等特殊卡型的 `B2` 取值规则另有区别（见 5.2、5.3）。




### 4.5 页3 / 页4：退房钟点与开反锁【反编译 + 实测】

原厂 `tem_readdatetime13_sdk`（0x10007BD1）反编译：

```c
v13[0] = BYTE14(v9) & 0xE0;          // 退房钟点 = 卡数据第 15 字节的高 3 位
v15 = sub_10002767(Str) + 11;        // 3 位值 + 11
v20 = (BYTE9(v9) & 0x20) != 0;       // 开反锁 = 卡数据第 10 字节的 bit5
```

`te_read` 实测布局为 `页1 | 页2 | 页3 | 页4 | 页5 | 页6(配置)`，因此：

| 字段 | 卡内位置 | 编码 |
|---|---|---|
| **退房钟点** | **页4[2] 的高 3 位** | `0x00`=11、`0x20`=12、`0x40`=13 … `0xE0`=18（3 位正好 8 档，对应文档「11~18」） |
| **开反锁** | **页3[1] 的 bit5** | 1 = 允许 |

**但 T5557 卡写不进这两页**（2026-11-08 实测，同一工具 `te_setuppwm_asc` + `te_writepwm_asc`）：

| 写哪页 | 返回码 | 读回 |
|---|---|---|
| 页1 | 0 | ✅ 生效 |
| 页3 | 0 | ❌ 无变化 |
| 页4 | 0 | ❌ 无变化 |

**后果**：现场 T5557 卡的 `tfzd` 恒为 `0` → **钟点恒 11**、反锁恒关。
而文档明确 `tfzd` 参与到期计算（「08:00 开卡、1 天、钟点 13 → 有效期至次日 13:00」），
所以**锁很可能在次日 11:00 就失效**，而发卡台界面显示 12:00（设置项只写数据库）。
真锁验证见 TD-149。

### 4.6 挂失（`gs`）：页1[2] 低 4 位【2026-11-08 实测确认】

原厂文档：

> **挂失**：1 为取消在用的客人卡（挂失），0 为不取消（不挂失）

反编译 `tem_writedoorcard13_sdk`：

```c
LOBYTE(v51[1]) &= 0xF0u;          // 先清低 4 位
if ( a6 != 0 ) ++LOBYTE(v51[1]);  // gs=1 → 低 4 位 = 1
```

**已解出**：`v51[1]` 就是卡内的 `页1[2]`（`p1[2]`）——**低 4 位 = 挂失标志**：
`0x00` 非挂失、`0x01` 挂失。实测样本（同一张卡只改这一位）：

| 卡字节 | `页1[2]` | RWCardDemo |
|---|---|---|
| `5BEC0000 81345BAA` | `0x00` | 非挂失 |
| `5BEC0100 81345BAA` | `0x01` | 挂失 |
| `5BEC0100 818143AB` | `0x01` | 挂失（201 房 / 1 天 / 14 点第 1 张，勾选「是否挂失」实写） |

2026-11-08 又补一组对照：勾选「是否挂失」写出的卡 `页1[2] = 0x01`（低 4 位 1），
同期不勾的卡（`5BEC0000…`、`5BECF000…`）低 4 位为 `0` —— **位与勾选状态一一对应，已确认**。

**原厂约定**（文档原文）：

> 若一个房间同时发三张卡，第一张卡对应挂失标志需置为 1，后两张卡该挂失标志位需置为 0

含义：**首卡会让该房间之前的所有在用卡失效**，后两张才能与它共存。

**我们的实现**（TD-150 起）：
- SDK：`CardBuilder.BuildGuestDay/Hour(..., bool lost, ...)` → `p1[2] = ((序号 & 0x0F) << 4) | (lost ? 1 : 0)`
- CLI：`PMSLockCard.exe issue --room 201 --days 1 --lost`
- 产品：发卡表单的「挂失卡（让本房间在用卡失效）」勾选框
- **已删除** `LowNibble`（`天数 & 3 == 1` 的伪规律）——它会让 **1 天卡和所有钟点卡被误标成挂失卡**

我们自己的实现里，`p1[2]` 的低 4 位（源码名 `low`）看起来很像这个标志：

```csharp
static byte LowNibble(int days, int hours)
{
    return (byte)(hours > 0 ? 1 : (((days & 3) == 1) ? 1 : 0));
}
p1[2] = ((序号 & 0x0F) << 4) | low;
```

但它的取值规律是「**天数 mod 4 == 1**」（14 个样本归纳），**与挂失语义对不上**，
所以不能认定它就是 `gs`。

| 待确认项 | 状态 |
|---|---|
| `gs=1` 在卡内的确切位置 | **未解**（需 IDA 追扰码表，或找能做 `gs=1` 写卡的环境对比字节） |
| 我们的 `low`（天数 mod 4）语义 | **未解**（可能是卡型细分或别的标志） |
| 发卡台是否支持挂失 | **不支持**，`CardBuilder` 没有该参数 |

> 原厂文档还提到「多个客人住同一间房时，第一张卡挂失标志置 1，后两张置 0」——
> 这只是场合适用的约定，具体编码仍取决于 `gs` 的落点。

### 4.7 「关扰码」实验：能找到开关，但解决不了互通（2026-11-08）

怀疑 RWCardDemo 写卡读不回来是因为扰码（`sub_1000A57B` 的 `D4F513CA987E60B2` 查表 + XOR 校验），
于是定位并改掉了两处 `config_parameter` 的模式参数：

| 地址 | 文件偏移 | 原字节 | 改后 | 位置 |
|---|---|---|---|---|
| `0x100038f4` | `0x38f4` | `6a 03`（push 3） | `6a 00` | `mif_selecom` |
| `0x1000bfa8` | `0xbfa8` | `6a 03`（push 3） | `6a 00` | `tem_readrfcardall_sdk` |

（`LcSDK.ini` 的 `ComEncryptFlag=0` 只能影响首次尝试，代码里还有 `config_parameter(-Value & 3)`
的自动回切逻辑，所以必须 patch 立即数。）

**结果**：写出的字节从 `669B09D1FA85…` 变成 `068BB9415A75…` —— 说明**路径确实变了**，
但**依然是「未知卡型」**，我们的解析器认不出。

**原因不是扰码，而是编码体系不同**：

| | 我们的卡（T5557） | 原厂 SDK 写的 |
|---|---|---|
| 寻址 | 房间序号（0..29） | **10 字符门锁编号**（如 `CA68067C30`） |
| 序号 | 16 位递增卡号 | **作业流水号 = 年月日时 + 小时内序号** |
| 布局 | `5B EC \| 序号 \| 时长码 \| 卡号 \| 年月日` | 位串拼装后再分块写入 |

**结论**：RWCardDemo **只能用来「读」我们的卡**（它按房号查 `LockID.ini` 得到门锁编号，
时间/钟点从我们卡字节解码），**不能用来「写」**——写出来永远是另一套体系。
因此「用原厂工具写卡对比字节」这条路走不通，钟点/反锁位置只能靠 §12.1 的反编译 + §12.3 的写页实验确认。

## 5. 卡型总表

### 5.1 客卡 / 钟点卡

```
页1 = 5B EC | ((序号 & 0x0F) << 4 | 低4位) | (序号 >> 4)
页2 = 时长码 | 卡号低 | 卡号高 | AB
```

### 5.2 总控卡

```
页1 = 5B EC F0 FF
页2 = 时长码 | 卡号低 | 卡号高 | AB
```

**时长码与客卡略有不同（实测 2026-11-05）**：

| 有效期 | 总控卡 | 客卡 |
|---|---|---|
| 1 小时 | **`0x41`** | `0x42` |
| 2 小时 | **`0x42`** | `0x43` |
| 3 小时 | **`0x43`** | `0x44` |
| 1 天 | `0x81` | `0x81` |
| 2 天 | `0x82` | `0x82` |

```
总控卡：小时 → 0x40 | 小时数        天 → 0x80 | 天数
客  卡：小时 → 0x40 | (小时数 + 1)   天 → 0x80 | 天数
```

即 **日租编码完全相同，只有小时编码差 1**（客卡多算一个"退房小时"）。

### 5.3 管理卡

| 卡型 | 页1 | 页2 |
|---|---|---|
| 复位卡 | `5B EC 0A 00` | `00 ｜ 卡号低 ｜ 卡号高 ｜ AB` |
| 清除卡 | `5B EC 9B E5` | `C7 ｜ 卡号低 ｜ 卡号高 ｜ AB` |
| 安装卡 | `5B EC ((序号 << 4) \| 0x0C) (序号 >> 4)` | `46 F2 00 01`（固定，无卡号） |
| 退房钟点设置卡 | `5B EC 7B <退房小时>` | `FF ｜ 卡号低 ｜ 卡号高 ｜ AB` |
| 校时卡 | `5B EC <值低> <值高>`（见下） | `14 ｜ 卡号低 ｜ 卡号高 ｜ AB` |

**新锁初始化顺序（现场规程）**

```
复位卡  →  清除卡  →  安装卡  →  校时卡
```

| 步骤 | 作用 |
|---|---|
| 复位卡 | 恢复出厂/空状态（实测：清空卡记录、高水位归零） |
| 清除卡 | 清除门锁信息（房间绑定等） |
| 安装卡 | 写入门锁信息（绑定到具体房间） |
| 校时卡 | 设定锁内时间基准，日卡/钟点卡据此计算到期 |

**校时卡编码（已解出，2026-11-05 四点验证）**

```
值   = 16 × 当日分钟数 + 953          （只记当日时/分，不含日期）
页1  = 5B EC (值 & 0xFF) (值 >> 8)
页2  = 14 ｜ 卡号低 ｜ 卡号高 ｜ AB
```

| 时间 | 分钟 | 值 | 页1 | 实测 |
|---|---|---|---|---|
| 15:05 | 905 | 15433 = 0x3C49 | `5BEC493C` | ✅ |
| 15:08 | 908 | 15481 = 0x3C79 | `5BEC793C` | ✅ |
| 15:10 | 910 | 15513 = 0x3C99 | `5BEC993C` | ✅ |
| 15:13 | 913 | 15561 = 0x3CC9 | `5BECC93C` | ✅ |

单位 1/16 分钟（3.75 秒）；10 秒内连发两张字节相同，说明按分钟取整。

**跨年三点验证（2026-11-08）**：三张校时卡的页1 与反算分钟如下，解出的**斜率恒为 16、截距恒为 953**，
说明公式在跨年份下成立（不是同一天四点拟合的巧合）：

| 流水号 | 页1 | 反算分钟 | 页2 | 卡号 |
|---|---|---|---|---|
| 2311081444（序号 4） | `5BECC93A` | 881（14:41） | `06C8434B` | 0x43C8 |
| 2510180844（序号 3） | `5BECC922` | 497（08:17） | `06C3434B` | 0x43C3 |
| 2611081544（序号 2） | `5BECC93E` | 945（15:45） | `06C2434B` | 0x43C2 |

三张的**页2 首字节均为 `0x06`、页2[3] 均为 `0x4B`**（与年份无关），卡号为 `0x43Cx`（低 6 位 = 发卡序号）。
卡内时间 = **实际写卡时刻**，与流水号填的时间可差 3–27 分钟。
页2 首字节 `0x14` 的含义未定（7 月样本为 `0x13`），暂按实测值照抄。

> **来源待确认的样本**：`5BEC493F14C843AB`（标注为「客卡」提供）——页1 `493F` 反算为 15:53 时间戳、
> 页2 首字节 `0x14` 不在任何时长码段，但末字节 `0xAB` 又是客卡标记。**三项互相矛盾，不作为任何结论依据**；
> 同批校时卡样本（`5BECC93A…` 等）与客卡正样本（`5BEC0100818143AB`）均已单独验证，结论以它们为准。

**复位卡（实测有效 · 2026-11-05）**

刷过复位卡后，锁会**清除该房间的卡记录**（把"当前有效卡号"归零）：

| 测试 | 结果 |
|---|---|
| 刷复位卡 0x0B82 → 刷 0x2B87（此前已被 0x2B88 顶掉） | ✅ **能开** |
| 接着刷 0x2B88 | ✅ 能开（复位后任意同房卡都有效） |
| 再刷 0x2B87 | ❌ 失效（0x2B88 重新建立了高水位） |

**结论**：
- 复位卡**不受卡号递增约束**（0x0B82 这种小号照样生效）
- 复位后高水位归零 → **任何一张该房间的卡都能开**，安全性上要保管好复位卡
- **卡号用尽（65536）时有解**：刷复位卡清零即可
- 总控卡是否也受这套高水位约束**尚未验证**（现场线索：可能不受限），见 §11.6

> 早期测试曾判断"复位卡刷 220 无反应"，那是因为只验证了"当前卡还能不能开"（复位前后都能开，看不出变化）。
> 正确的验证方法应当是：**先用大号卡顶掉一张小号卡，再刷复位卡，看那张小号卡是否恢复**。

**安装卡说明**

房号**只**编码在页1的序号里，页2 是固定值 `46 F2 00 01`，与房号无关（2026-11-05 实测三个房间）：

| 房号 | 序号 | 页1 | 页2 |
|---|---|---|---|
| 201 | 0 | `5BEC0C00` | `46F20001` |
| **259** | **38** | `5BEC6C02` | `46F20001` |
| 220 | 15 | `5BECFC00` | `46F20001` |

- 只写"房间序号"，**不包含** `LockID.ini` 里的 5 字节门锁 ID。
- 页2 结尾为 `0001` 而非 `AB`，是安装卡独有的签名。
- `00 01` 的语义（楼栋 / 楼层 / 版本）**未确认** —— 本现场只有 1 栋 1 层
  （`Kf_fh.FLhbh=000`，30 间房全在二楼），任何"按楼栋/楼层变化"的字段都观测不到差异。
  若要验证需另建楼层或楼栋，不建议在生产库上做。
- 现网所有房间的安装卡可以**统一照抄**这个固定页2。
- **`00 01` 与"每房可发卡数"无关**（2026-11-07：设 2/5/10/0 各发一张，页2 均为 `46F20001`）。


**退房钟点卡**
- 第 4 字节就是退房小时：12 点→`0C`，14 点→`0E`。

**校时卡**
- 完整编码见本文件 §5.3 表格下方与 §9，已解出并实测四点命中。

## 6. 卡号与锁的关系（**已实测确认**）

### 6.1 结论

> **锁对每一种卡型（日租 / 钟点）分别记住一个"当前有效卡号"。**
>
> | 新卡的号 | 结果 |
> |---|---|
> | **大于**当前有效号 | ✅ 开，并更新为新的有效号 |
> | **等于**当前有效号 | ✅ 开（就是那张卡本身） |
> | **小于**当前有效号 | ❌ 拒 |
>
> **不同卡型互不影响**（日租卡顶不掉钟点卡，反之亦然）。

这就是所谓"防重放"的全部机制 —— 本质是 **每个房间、每种卡型只保留最新一张**。

### 6.2 实测证据（2026-11-05，220 房）

**测试 A：日租 vs 钟点 互不影响**

| 顺序 | 卡 | 类型 | 卡号 | 结果 |
|---|---|---|---|---|
| ① | 我们的日租卡 | 日租 | 0x2B42 | ✅ |
| ② | 软件的钟点卡 | 钟点 | 0x2B84 | ✅ |
| ③ | 我们的日租卡 | 日租 | 0x2B42 | ✅（**未受影响**） |

**测试 B：同类型（日租）大号顶小号**

| 顺序 | 卡 | 卡号 | 结果 |
|---|---|---|---|
| ① | 我们的日租卡 | 0x2B42 | ✅ |
| ② | 软件的日租卡 | 0x2B85 | ✅ |
| ③ | 我们的日租卡 | 0x2B42 | ❌ **被顶掉** |

**测试 C：同类型（钟点）大号顶小号**

| 顺序 | 卡 | 卡号 | 结果 |
|---|---|---|---|
| ① | 软件的钟点卡 | 0x2B86 | ✅ |
| ② | 我们的钟点卡 | 0x2B88 | ✅ → 有效号变 0x2B88 |
| ③ | 软件的钟点卡 | 0x2B86 | ❌ |
| ④ | 我们的钟点卡 | 0x2B88 | ✅（**等于**有效号也能开） |
| ⑤ | 软件的钟点卡 | 0x2B87 | ❌ |

**测试 D：复位卡可以清零高水位**

| 顺序 | 操作 | 结果 |
|---|---|---|
| ① | 刷复位卡（0x0B82） | 生效 |
| ② | 刷钟点卡 0x2B87（此前已被 0x2B88 顶掉） | ✅ **恢复可用** |
| ③ | 刷钟点卡 0x2B88 | ✅ |
| ④ | 再刷 0x2B87 | ❌ 又被顶掉 |

→ **复位卡清空该房间的卡记录**；之后任意一张同房卡刷入都会重新建立高水位。

### 6.3 历史现象的重新解释

早期记录里 `0x2446` 在 `0x2447` 之后被拒 —— 当时误以为是"全局递增"，实际是：
两张都是**钟点卡**，`0x2446 < 0x2447`，同类型被顶掉。与"日租/钟点分治"完全吻合。

### 6.4 混用策略（原软件 + 本 SDK）

软件的发号规律（实测）：

- 每次发卡 **+1**（0x2B86 → 0x2B87 → 0x2B88，不看锁、不跳号）
- 软件重启后可能向前跳一段（实测 +62 / +64 / +1790 都出现过）
- 与我们**完全独立**，它不知道我们发过什么

因此：

| 做法 | 评价 |
|---|---|
| 号紧贴软件序列（相差 0~2） | ✅ **推荐**。偶发撞号＝多一张重复卡，无实质影响 |
| 领先 1~5 号 | ✅ 可以。软件的卡短暂失效几张即追平（因为"+1"很快） |
| 跳到 0x4701 这种量级 | ❌ **禁止**。同类型软件卡要废几千张才追回来 |

**撞号（两边同号）的后果**：两张物理卡都能开（锁分不出来），下次任一方发出更大的号时同时失效 —— 等价于"多一张副卡"。

### 6.6 两个"逃生通道"

| 场景 | 解法 |
|---|---|
| 号跳飞了（比如跳到 0x4701），软件卡长期失效 | 刷**复位卡**清零高水位，让软件重新开始 |
| 卡号用尽（65536 用满） | 刷**复位卡**清零，可再用一轮 |

> 复位卡不受卡号递增约束（实测 0x0B82 这种小号照样生效），但**必须妥善保管** ——
> 任何拿到复位卡的人都能让房间的旧卡重新生效。

### 6.5 卡号空间与用尽处置

- 16 位，**65536 个**（`0x0000`~`0xFFFF`）；
- 原软件按 +1 递增，实测约 **85 号/天** → 约 **2 年 1 个月**用尽；
- 溢出后推测**回绕到 0x0000**（未实测），此时锁内高水位仍在 `0xFFxx`，新卡全部被拒；
- **处置：回绕后逐把锁刷复位卡**（高水位清零），之后小号卡即可继续使用；
- **不可提前复位** —— 提前复位后软件继续涨到 0xFFFF 再回绕，问题依旧；
- 复位卡页1 固定 `5BEC0A00`，不含房号，**一张可刷遍全楼**；
- 复位会使该锁所有旧卡立刻失效，只能挑空房时段做。

详细运维流程见根目录 `README.md` 第十二节。

- 30 间房，序号有跳号（12/14/18/26/27/30/31/32/34/36 为历史删除房间留下的空位）。

## 11. 待验证项

> 以下均为**不影响发卡功能**的遗留问题，按需要再补。

### 11.1 钟点卡 / 日租卡到期语义（未做最终验证）

已知事实：

- 1 小时卡**发卡 65 分钟后**才首刷，仍能开门 → 说明**有效期从"首次刷卡"起算，不是从发卡**。
- 但同一张卡**首刷后 3 小时 22 分**复刷**仍能开门** → 说明锁当时**还不会判过期**。

推测（未验证）：锁内缺少可用的时间基准，因此无法计算到期；刷过**校时卡**后应当会按时失效。

> 建议的验证步骤（未执行）：刷校时卡 → 发 1 小时卡 → 首刷 → 等 1 小时 → 复刷。

### 11.2 清除卡 / 安装卡的实际效果（未验证）

| 卡 | 字节 | 推测作用 |
|---|---|---|
| 清除卡 | `5BEC9BE5` + `C7…AB` | 清除门锁信息（房间绑定） |
| 安装卡 | `5BEC((序号<<4)\|0x0C)(序号>>4)` + `46F20001` | 写入门锁信息（绑定房间） |

字节已与原厂一致，但我们**没有在锁上验证过它们的实际效果**。
风险：刷清除卡可能让锁变"未安装"，需要安装卡恢复。

### 11.3 钟点卡页1低4位（0 / 1）

8 个样本中 3 次为 `0`、5 次为 `1`，**规律未解**。
两种值锁都能开，不影响功能，只是与软件字节不完全一致。

### 11.4 校时卡页2首字节

实测今天为 `0x14`，2025-07 的旧样本为 `0x13`，含义未定（可能与日期/年份有关）。
生成时按实测值照抄即可。

### 11.5 未抓包的卡型

应急码设置卡、楼栋开门卡、楼层开门卡、应急开门卡、通道开门卡 —— **均无样本、格式未知**，详见 §5.4。

### 11.6 总控卡是否受客房卡高水位限制（待测试）

**现状【待定】**：客房卡的判定已实测为「每房间 × 每卡型各自维护高水位」（§7），但**总控卡是否也受这套高水位约束，尚未验证**。

已知事实：

- 总控卡页1 为 `5B EC F0 FF`，序号位置是 `F0FF`（房间序号最大 255，正常房卡不可能取到），
  看起来是**独立标记**而非"序号 4095 的房间"；
- 现场反馈：**管理总控卡可能不受客房水位线限制**——即卡号低于该房间已有高水位时，
  总控卡仍能开门。此说法**未做受控实验**，目前只能当线索。

若该线索成立，会直接影响两处实现判断：

1. **卡号治理**：总控卡发卡号低不必担心被拒，产品侧水位告警文案可相应放宽；
2. **有效性推算**：总控卡不会因为"房间已有更高卡号"而失效，到期提醒口径不受房间高水位影响。

> 建议的验证步骤（未执行）：取一间已有高水位的房间（先刷一张 `0x2Bxx` 客卡建立水位）→ 发一张**卡号更小**的总控卡（如 `0x24xx`）→ 刷同一把锁，看是否开门。
> 对照组：同卡号量级的客卡刷同一把锁（预期被拒）。结果补进 §7 与本表。

## 14. 授权与合规（技术事实）

### 14.1 授权在哪里

本软件确实有授权机制，但它位于**应用层**，不在读卡器驱动里：

| 模块 | 是否涉及授权 | 证据 |
|---|---|---|
| `KeyPro.dll`（241 KB） | **是**，授权模块 | 导入 `DeviceIoControl` + `CreateFileA` + `CH341PT.dll!CH341PtNameIsCH341` → 访问**硬件加密狗**；同时用 ADVAPI32 读写注册表、用 `CreateToolhelp32Snapshot/OpenProcess/TerminateProcess` 做进程检查 |
| `SmartLock.dll`、`NacreHis.exe`、`HisServo.exe`、`DbDataTool.dll` 等 11 个模块 | 引用 KeyPro | 二进制内包含 `KeyPro` 字符串 |
| **`LC32RFRW.dll`（读卡器驱动）** | **否** | 只导入 `KERNEL32.dll` + `USER32.dll`（共 77 个函数），无 ADVAPI32（注册表）、无 `KeyPro` 字符串、无设备 I/O 之外的授权探测 |

### 14.2 我们的方案为什么不触发授权

SDK 只调用 `LC32RFRW.dll` 的底层导出（`mif_selecom` / `te_read_asc` / `te_setuppwm_asc` / `te_writepwm_asc` 等），
**不加载 `KeyPro.dll`、不调用 `SmartLock.dll` / `SM_RW_Card.dll` 的 `Do*` 业务接口**。

**实测证据（无授权的机器上）**：本机（未安装加密狗、无授权）通过 COM3 成功完成
"读卡 → 设密码 → 写页1 → 写页2 → 回读校验"，卡上数据由 `5BECF0FF814822AB` 变为 `5BECF100429922AB`，
新进程回读一致；多次读卡亦正常。

### 14.3 风险与边界

1. **技术可行 ≠ 合同允许**。厂商可能主张"调用接口需授权"，即使技术上绕过了 `KeyPro`。
   这一点属于商务/法务判断，不在本技术文档范围内。
2. **版本冻结**：上述结论只对 SHA-256 为
   `F2F483E08BA8048FFD1C57E66CB35D9E32C1C1E280DC5F2FF100A5D881BCCBC0` 的 `LC32RFRW.dll` 成立。
   若厂商升级驱动加入授权校验，需重新评估。
3. **部署建议**：现场使用与该版本一致的驱动文件；升级前先在测试机验证 SDK 的 `selftest` 与一次真实读写。
