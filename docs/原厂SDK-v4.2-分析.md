## 3. 参数语义（【原厂文档】原文要点）

| 参数 | 含义 | 取值范围与规则 |
|---|---|---|
| `BH` | 门锁编号 | **10 字符**，锁的唯一标识（不是房号） |
| `fksj` | 发卡时间 | 年月日时各两位，共 8 字符，例：`04080910` = 2004-08-09 10 时 |
| `xh` | 一小时内发卡序号 | **0–62**；超过 63 次则 `fksj` 小时 +1、序号从 0 重来 |
| `sjdw` | 时间单位 | **0=小时，1=天，2=月，3=年**；其它值按「天」 |
| `sjlength` | 时间长度 | 1–63 小时 / 1–63 天 / 1–15 月 / 1–3 年 |
| `gs` | 挂失标志 | 1 = 取消在用的客人卡（挂失），0 = 不取消 |
| `tfzd` | **退房钟点** | **11–18**；例：13-01-01 08:00 写 1 天、钟点 13 → 有效期到 13-01-02 13:00 |
| `fs` / `OpenInner` | **是否允许开反锁** | 0 = 不允许，1 = 允许 |
| `p_nLockAP` | 系统标识号 | 二级代理商模式才有效，其它填 0；对应 `LockID.ini` 最后的 `LockAP=` |

**关键规则（原厂原文）**

1. 「卡中作业流水号必须**大于等于**门锁电路板中作业流水号，否则开门失败」——
   与我们实测的「大于→开并更新、**等于→开**、小于→拒」**完全吻合**【实测印证】。
2. 「作业流水号 = 日期时间中的年月日时 + 1 小时内所发卡的序号」——**流水号带时间戳**，
   不是纯递增计数器。
3. 多客人同房：**第一张卡挂失标志置 1，后两张置 0**（同一房间最多 3 张）。
4. **退房回收卡**（原文）：「客人退房时仍可调用此函数…此时 `BH`=实际门锁编号，
   `fksj=00000000, xh=0, sjdw=0, sjlength=1, gs=0` 即实现退房回收卡片功能」。
5. 钟点房的退房时间不受 `tfzd` 限制，`tfzd` 填 11–18 任意值即可。
6. 授权：未授权读写卡返回 **128**；用非专用接口读卡器返回 **129**。
7. 总卡 / 栋卡 / 层卡：**同一个写卡函数**，只换 `BH`（门锁编号）。
8. `LockID.ini` 由 `GetLockID.exe` 从原厂门锁软件工作目录导出：左边房号、右边门锁编号，
   末行 `LockAP=X`。

## 4. 与现有实现的对比

### 4.1 已完全印证的部分（我们的逆向结论正确）

| 我们的结论 | 原厂文档 | 状态 |
|---|---|---|
| 锁按「房间 × 卡型」记高水位，大于→开并更新、等于→开、小于→拒 | 「作业流水号必须 ≥ 锁内值」 | ✅ 一致 |
| 卡内 16 位序号（`5B EC` 后两字节）| 「作业流水号」 | ✅ 同一概念 |
| 同房多卡有特殊标志位 | 「多客人同房第一张挂失标志置 1」 | ✅ 解释了我们观察到的现象 |
| `config_parameter(0)` 明文模式 | `config_parameter` 导出 + 我们实测 | ✅ 一致 |
| EM4305 底层读写 | `em4305_*` 全套导出 | ✅ 一致 |

### 4.2 我们缺失 / 不同的部分（**重点**）

| # | 原厂能力 | 我们的实现 | 影响 |
|---|---|---|---|
| 1 | **退房钟点写在卡里**（`tfzd`，11–18） | 只存数据库算 `expires_at`（TD-126），卡里不写 | **锁不知道退房钟点**；我们之前认为「卡里只有时长码」可能不完整——页2 第 4 字节 `AB` 是否为钟点/标志编码，**需重新核查**【待验证】 |
| 2 | **开反锁标志**（`fs`/`OpenInner`） | 完全没有 | 新能力，可能需要新增卡型参数 |
| 3 | **时间单位支持月/年**（`sjdw` 0/1/2/3） | 只有天/小时；月/年用固定天数档位近似（90/120/360/1095） | 1095 天 ≈ 3 年但非精确月年 |
| 4 | **序号按「小时内 0–62」分段**（超 63 则小时 +1） | 全局单调递增计数器（`CardNo.state`） | 我们不复位，锁只比大小，实测可用；但与原厂流水号规则不同 |
| 5 | **流水号含发卡时间戳**（`fksj` 8 字符） | 序号无时间信息 | 影响「作业流水号存挡」的对账能力 |
| 6 | **退房回收卡用特定参数组合**（`fksj=00000000, xh=0, sjdw=0, sjlength=1, gs=0`） | 用全零 raw（`--p1 00000000 --p2 00000000`） | **字节可能不等价**：原厂 `sjlength=1, sjdw=0` 意味着时长码非零【待验证】 |
| 7 | 授权机制（128/129 错误码） | 无（我们的 CLI 直接调驱动） | 原厂 SDK 有授权限制，我们的方案绕过了 |

### 4.3 对我们最有价值的三条

1. **页2 第 4 字节（我们记作 `AB`）很可能是 `tfzd`/`fs` 的编码位**——若成立，我们的卡在
   「退房钟点非 12 点」时可能与锁的理解不一致。**建议用原厂 `RWCardDemo.exe` 写一张
   退房钟点 13 点的卡，与我们的卡逐字节比对**【待验证】。
2. **退房回收卡的官方参数**说明「全零」可能不是正确写法（原厂 `sjlength=1`），
   需要用原厂演示程序写一张回收卡抓字节验证【待验证】。
3. **`tem_writedoorcard13WithRec_sdk`** 说明原厂写卡时**同时写一条记录**（可能是卡内或软件侧），
   与我们「issuance 表只追加」的思路一致，但卡内是否有记录区未知【待验证】。

## 5. 结论

- 原厂这套 SDK 是**授权 + 门锁编号**模式（`BH` 是 10 字符门锁编号，不是房号），
  与我们「房号 → 序号」的方案是两套编码体系；**不能直接替换** `sdk/PMSLockSDK.cs`。
- 但它是**权威语义来源**：`tfzd`、`fs`、`sjdw`、`gs`、`xh` 五个参数解释了我们逆不出来的部分。
- 我们与它在「高水位」判定上完全一致，说明核心机制无误。
- 待验证项集中在**卡内字节的钟点/反锁/挂失编码**——需要用原厂 `RWCardDemo.exe` 抓样本。

## 7. IDA 反编译进展（2026-11-08，ida-mcp）

对 `LCRFRV_SDK.dll` 反编译了写卡链路，**确认了 `tfzd` 与 `fs` 的编码方式**（不再依赖猜测）：

### 7.1 调用链

```c
// 0x1000cade
tem_writedoorcard13_sdk(Src, a2, xh, sjdw, sjlength, gs, LockAP, tfzd, fs)
{
    byte_1001FED4   = fs;      // 开反锁 → 全局 1 字节
    dword_1001FED8  = tfzd;    // 退房钟点 → 全局 4 字节
    dword_1002000C  = 3;       // 卡格式版本标记
    return tem_writedoorcard_sdk(...);   // 基础版：把 tfzd/fs 从全局取用
}

// 0x1000853e → 0x10008885（真正的字节构造，9191 字符反编译体）
tem_writedoorcard_sdk → sub_10008885(Src, fksj, xh, sjdw, sjlength, gs)
```

`dword_1001FED8`（tfzd）的引用点：`sub_10008885`（0x10009153）、`tem_writedoorcard13WithRec_sdk`、
`Lc_writedoorcard13_sdk`。
`byte_1001FED4`（fs）的引用点：`sub_10008885`（0x1000933c）等。

### 7.2 `tfzd`（退房钟点）的编码【IDA 反编译】

```c
v17 = dword_1001FED8 - 11;                    // tfzd - 11
if ( dword_1001FED8 - 11 < 0 || v17 > 7 )
    v17 = 1;                                   // 越界（不在 11..18）→ 取 1（即 12 点）
...
sub_10002E3C(v17, KeyName, 3);                 // 转成 3 位二进制串（'0'/'1'）
sub_10002ABD(KeyName, KeyName);                // 反转
memcpy((char *)&v27[2] + 5, KeyName, 3u);      // 写进位串工作区 offset 21..23
```

**结论：`tfzd` 不是整字节，而是「`tfzd - 11` 的 3 位二进制」**（11→000, 12→001, … 18→111），
越界值一律按 `1`（12 点）处理。**3 位正好覆盖 8 个钟点，与文档「11~18」完全吻合。**

### 7.3 `fs`（开反锁）的编码【IDA 反编译】

```c
memcpy((char *)&v27[1] + 4, a1_0, 1);            // offset 12 = '1'
if ( byte_1001FED4 != 0 )
    memcpy((char *)&v27[1] + 5, a1_1, 1);        // fs≠0 → '1'
else
    memcpy((char *)&v27[1] + 5, a0_2, 1);        // fs=0  → '0'
memcpy((char *)&v27[1] + 6, a0_3, 1);            // offset 14 = '0'
memcpy((char *)&v27[1] + 7, a0_4, 1);            // offset 15 = '0'
```

常量实测值：`a0_1/a0_2/a0_3/a0_4 = '0'`，`a1_0/a1_1 = '1'`（`.rdata` 逐字节读取）。

**结论：`fs` 是位串里的 1 个 bit（offset 13）**，紧邻三个固定位（'1','0','0'）。

### 7.4 底层拼字节的机制【IDA 反编译】

- `sub_10002E3C(v, buf, n)` = **整数 → n 位二进制字符串**（低位先出，不足左补 '0'）
- `sub_10002ABD(s, dst)` = **字符串反转**（因为上一步是低位先出）
- `sub_10002767(s)` = **二进制串 → 整数**（从串尾读，串尾 = bit0 / LSB）

所以原厂是「**按位拼一张 32 位的表，再解析成 4 字节**」——这与我们逆向出的
`页1 = 5B EC | ((序号&0x0F)<<4 | 低4) | (序号>>4)`、`页2 = 时长码|卡号低|卡号高|AB`
这种「位段拼接」结构**同源**，但**字段顺序与位宽不同**。

### 7.5 已经能下的结论

1. 我们的卡**没有写 `tfzd` 与 `fs`** —— 已从代码层面证实（不是猜测）。
2. `AB`（页2 第 4 字节）**不是**钟点字段：`tfzd` 是 3 位、`fs` 是 1 位，都在 32 位位串的中段，
   跨字节分布，与「整字节 AB」不对应。
3. 原厂的位串布局与我们不同（原厂把 `tm_hour/tm_mday/tm_mon/tm_wday/年` 也塞进位串，
   那是**「作业流水号含时间戳」**的实现；我们是纯 16 位序号）。

### 7.6 还差一步（需继续或实测）

- 精确的「位 offset → 卡内字节」映射还没闭合：需要确认 `sub_10008885` 的哪次调用产出页1、
  哪次产出页2，以及 `mif_write`/`em4305_write` 收到的 8 字节是哪个缓冲。
- 也可以走实测更快的路：用原厂 `RWCardDemo.exe` 写「钟点 12 / 13、反锁 0 / 1」四张卡，
  直接看 8 字节哪一位翻转（TD-140）。两条路互为验证。

## 8. 位 offset → 卡内字节对照表（TD-141，2026-11-08）

> 证据来源：`ida-mcp` 反编译 `sub_10008885`(0x10008885)、`sub_1000A57B`(0x1000A57B)、
> `sub_1000C7B6`(0x1000C7B6)、`sub_10002E3C`/`sub_10002ABD`/`sub_10002767`。
> 标注：**【反编译】** = 代码直接读到；**【推断】** = 由代码结构归纳；**【待验证】** = 需实测。

### 8.1 完整编码链是三层，不是一层

```
① 明文字段 → v51[0..15]        位运算直接拼字节（行 106~121）
② v51 → sub_1000A57B           hex 字符查表扰码（表 D4F513CA987E60B2）+ XOR 校验
③ 扰码结果 → sub_1000C7B6      按 4 字节分块写 EM4305，起始 block 5，共 4 块 = 16 字节
```

**这是本节最重要的结论**：原厂卡内字节 **不等于** 明文字段直接拼接，中间隔着一层查表扰码。
我们 `sdk/CardBuilder` 产出的是**卡内最终字节**（逆向时从原厂卡读出来再复现），
所以「明文 offset」与「我们的哪个字节」之间**还差一次反扰码**，不能直接对标。

### 8.2 明文层布局（v51，16 字节）【反编译】

行 106–121 是直接的位运算（`a3` = xh、`a5` = sjlength、`a6` = gs）：

```c
*(_QWORD *)v51 = *Src;                                  // v51[0..3] = BH 门锁编号前 4 字节
LOBYTE(v51[1]) &= 0xF0u;                                // 清 v51[1] 低 4 位
if ( a6 != 0 ) ++LOBYTE(v51[1]);                        // gs → v51[1] 低 4 位
LOBYTE(v51[2]) = (a5 & 0x3F) + v37;                     // sjlength → v51[2] 低 6 位
HIBYTE(v51[2]) = a3 + (HIBYTE(v51[6]) << 6);            // xh 低 2 位 → v51[2] 高字节
LOBYTE(v51[3]) = (((int)HIBYTE(v51[6]) >> 2) & 7) + 8 * LOBYTE(v51[6]);  // xh 高位
HIBYTE(v51[3]) = (HIBYTE(v51[5]) & 0xF) + 16 * LOBYTE(v51[5]);
LOBYTE(v51[5]) = (v51[5] & 0xF) + 10 * (LOBYTE(v51[5]) >> 4);            // fksj BCD 交换
HIBYTE(v51[5]) = (HIBYTE(v51[5]) & 0xF) + 10 * (HIBYTE(v51[5]) >> 4);
LOBYTE(v51[6]) = (v51[6] & 0xF) + 10 * (LOBYTE(v51[6]) >> 4);
HIBYTE(v51[6]) = (HIBYTE(v51[6]) & 0xF) + 10 * (HIBYTE(v51[6]) >> 4);
```

| v51 位置 | 位 | 字段 |
|---|---|---|
| `v51[0..3]` | — | BH 门锁编号（`*(_QWORD *)v51 = *Src`） |
| `v51[1]` | **bit0–3** | **`gs`（挂失）** |
| `v51[2]` | **bit0–5** | **`sjlength`（时长）** |
| `v51[2]` 高字节 | bit0–1 | **`xh` 低 2 位** |
| `v51[3]` | bit0–2 | `xh` 高位（含移位） |
| `v51[5..6]` | — | `fksj`（年月日时，BCD 交换后） |

### 8.3 两条写卡分支（`dword_1002000C >= 3` 时进入）

位串 `v27` 的规则（三个转换原语已确认）：**每 8 个 `'0'/'1'` 字符 = 1 字节，字符 0..7 依次是 bit0..bit7**
（`sub_10002ABD` 反转 + `sub_10002767` 从串尾读，串尾 = bit0）。

#### 分支 A（行 214–221）→ 写 `v51[4..7]`，含 `fs`

| v27 offset | 宽度 | 字段 |
|---|---|---|
| 0–3 | 4 | `v30`（ini 配置项） |
| 4–7 | 4 | `v29`（ini 配置项） |
| 8–11 | 4 | `v28`（ini 配置项） |
| 12 | 1 | 固定 `'1'` |
| **13** | **1** | **`fs`（开反锁）** |
| 14–15 | 2 | 固定 `'0'` |
| 16–23 | 8 | `v13`（ini 配置，2 字节） |
| 24–29 | 6 | `v27` 前 6 位（回环） |
| 30–31 | 2 | `tm_hour` 低 2 位 |

→ `fs` 在块 1 的第 5 个字符 → **bit5** → 写入 `v51[4+1]` = **`v51[5]` 的 bit5**

#### 分支 B（行 222–255）→ 写 `v51[6..9]`，含 `tfzd`

| v27 offset | 宽度 | 字段 |
|---|---|---|
| 0–2 | 3 | `tm_hour` 低 3 位 |
| 3–7 | 5 | `tm_mday` |
| 8–11 | 4 | 月 |
| 12–14 | 3 | `tm_wday` |
| 15–20 | 6 | 年 |
| **21–23** | **3** | **`tfzd - 11`（0..7）** |
| 24–31 | 8 | 固定 `'0'` |

→ `tfzd` 在块 2 的第 5–7 个字符 → **bit5–bit7** → 写入 `v51[6+2]` = **`v51[8]` 的 bit5–7**

### 8.4 扰码层（`sub_1000A57B`）【反编译】

```c
qmemcpy(&v16[36], "D4F513CA987E60B2", 16);     // 16 字节查表
v13 = 8; if ( a3 >= 3 ) v13 = 19;               // 卡格式版本影响校验值
for ( i = 1; i < 15; ++i ) {                    // 15 个字节 XOR
    sscanf(&Buffer, "%x", &v15);
    v10 ^= v15;
}
v10 ^= dword_10020004 ^ v13;                    // 再混入 sjlength 与版本
sprintf(v14, "%02X", v10);                      // 校验和 → v5[30..31]
for ( i = 0; i < 32; ++i ) {                    // 逐 hex 字符查表替换
    sscanf(&Buffer, "%x", &v17);
    v12[i] = v16[v17 + 36];
}
```

→ 32 个 hex 字符逐个被表 `D4F513CA987E60B2` 替换，末尾附 2 字符 XOR 校验。

### 8.5 最终写卡（`sub_1000C7B6`）【反编译】

```c
v12 = 4;  if ( dword_1002000C == 0 ) v12 = 2;   // 13 版写 4 块，旧版写 2 块
if ( a1 == 6 ) { em4305_login_asc(密码); v6 = 5; }   // EM4305 起始 block 5
for ( i = 0; i < v12; ++i ) {
    v10[0] = *(_DWORD *)&Src[4 * i];
    em4305_write(i + v6, v10);                  // 写 block 5,6,7,8（共 16 字节）
}
// 随后 em4305_read 回读校验，失败重试（共 3 轮）
```

**13 版写卡写 16 字节（block 5..8）**，不是 8 字节。

### 8.6 与我们卡格式的对照

| 项 | 原厂 | 我们 |
|---|---|---|
| 写入长度 | **16 字节**（EM4305 block 5..8） | **8 字节有效**（页1、页2），页3–7 全 0 |
| 明文层 | `v51[0..15]` 位运算拼装 | 无（直接生成最终字节） |
| 扰码 | `D4F513CA987E60B2` 查表 + XOR 校验 | 无（我们的字节 = 逆向读出的最终值） |
| 退房钟点 | `tfzd-11` 占 3 位 | **不写**（只在库里算 `expires_at`） |
| 开反锁 | 1 bit | **不写** |
| 挂失 | `gs` 占 4 位 | 用「同房首卡 + 序号」近似 |
| 时间戳 | `fksj`（年月日时）进明文层 | 无（纯 16 位递增序号） |

### 8.7 能下的结论

1. **原厂写 16 字节，我们只写 8 字节**——这是目前发现的最大结构差异。`tfzd`/`fs` 所在的
   `v51[5]`、`v51[8]` 落在第 2 块与第 3 块，**只写 2 块时这些字段本来就没地方放**【推断】。
2. `AB`（我们页2 第 4 字节）**不是**钟点字段——钟点在明文层是 `v51[8]` 的 bit5–7，且要过扰码层。
3. 要「加一个字段」不是简单改一位：明文字段 → 位串 → 查表扰码 → XOR 校验 → 分块写入，任何一环都要跟上。
4. 「我们的字节 ↔ 原厂明文 offset」的对应还差一次**反扰码**，需要样本才能锚定【待验证】。

### 8.8 交给 TD-140 验证的五件事

**第 0 步（新增，前置）**：**先确认芯片类型**。本 SDK 的 `LcSDK.ini` 是 `CardType=6` → EM4305 路径；
而现场卡是 TEMIC（T5557/5567），走 `te_*` 命令集。**芯片不同，块/页结构不同**（见 §9）。
在没确认「这份 SDK 能不能驱动现场卡」之前，下面 4 步都无从谈起。

1. 用原厂写「钟点 12 / 13」两张卡，读回 **16 字节**（不是 8），看 `v51[8]` bit5–7 扰码后对应哪个字节的哪一位。
2. 用原厂写「反锁 0 / 1」两张卡，验证 `v51[5]` bit5。
3. 确认 block 7 / block 8 在我们这边是否被写入（`te_setuppwm_asc` 路径能否写到 block 7+）。
4. 若 block 7/8 是空的，判断锁是否会因缺这两块而忽略钟点/反锁字段。

### 8.9 实测修正（2026-11-08，物理样本）

用 patch 过授权的 `RWCardDemo.exe`（只读）+ 我们自己的写卡工具做交叉验证，纠正 §8 两处静态推断：

**① 钟点/反锁的实际位置（读卡侧反编译 + 实测）**

```c
// tem_readdatetime13_sdk（0x10007BD1）
v13[0] = BYTE14(v9) & 0xE0;    // 钟点 = 第 15 字节高 3 位，+ 11
v20    = (BYTE9(v9) & 0x20) != 0;   // 开反锁 = 第 10 字节 bit5
```

`te_read` 实际布局为 `页1 | 页2 | 页3 | 页4 | 页5 | 页6(配置)`，所以：

| 字段 | 卡内位置 | 编码 |
|---|---|---|
| 退房钟点 | **页4[2] 高 3 位** | `0x00`=11、`0x20`=12、`0x40`=13 … `0xE0`=18 |
| 开反锁 | **页3[1] bit5** | 1 = 允许 |

**② 页2 第 4 字节不是固定 `AB`，它装的是「年份 + 月日」**

| 改动 | 实测效果 |
|---|---|
| `AB`→`0B`（清 bit7、bit5） | 年份 **2026 → 2016**（bit7 = 年 +8，bit5 = 年 +2） |
| `AB`→`A0`（清低 4 位） | 月/日变 `00` → RWCardDemo 报 `Run-time error '13'` |
| 页1[3] `00`→`01` | 房号/序号变，钟点不变 |

**③ T5557 卡只有页1、页2 可写**

同一工具（`te_setuppwm_asc` + `te_writepwm_asc`）逐页写：

| 页 | 返回码 | 读回 |
|---|---|---|
| 页1 | 0 | ✅ 生效 |
| 页3 | 0 | ❌ 无变化 |
| 页4 | 0 | ❌ 无变化 |

→ **现场 TEMIC/T5557 卡上，钟点与反锁字段位于写不进去的页3/页4，因此恒为默认值（钟点 11、反锁关）。**
这也解释了为什么 RWCardDemo 再怎么读都显示「退房钟点 11」——不是我们漏写，而是这张卡根本没有可写的钟点区。

> 完整样本与复现步骤见 `docs/抓包样本与验证记录.md` §12。

## 8.10 `ComEncryptFlag` → `dword_1002000C` → 写卡扰码（2026-11-08 源码级确认）

之前一直没搞清「为什么同一张校时卡，demo 写出来 `页2[0]=0x06`、原厂软件写出来 `0x10`、我们照抄的是 `0x14`」。
答案在 `mif_selecom`（打开串口时执行一次）：

```c
// 0x10003691  mif_selecom
FileName = <SDK 目录> + "LcSDK.ini";
Stream = fopen(FileName, "r");
if (Stream != NULL) {
    v = GetPrivateProfileIntA("System", "ComEncryptFlag", 2, FileName);  // 缺省 2
    if (v >= 4) v = 2;                    // 只接受 0/1/2/3
    dword_1002000C = v;

    dword_1002000C = 3;                   // 没有 ini 时默认 3
}
```

写时钟卡时（`tem_writetimercard_sdk` @ 0x10007154）：

```c
LOBYTE(v14[2]) = 6;                       // 明文页2[0] 是 0x06
...
if (dword_1002000C > 0)
    sub_1000A57B(v14, Src, 2);            // 整体扰码（D4F513CA987E60B2 查表 + CRC）
sub_1000C7B6(..., v14);                   // 写卡
```

**所以 `0x06` 是明文，`0x10` 是加扰后的同一字节。**

| 写入方 | `LcSDK.ini` 的 `ComEncryptFlag` | 页2[0] | 页2[3] |

| 我们的 `CardBuilder` | 不走 SDK，直接拼字节 | `0x14`（照抄某次加扰结果） | `0xAB` |

## 9. 两套实现对比：为什么串口抓包只有 2 页（2026-11-08）

> 用户提问：「为什么逆向抓包 hook 时只有前两页的数据？」——这一节回答它，并修正 §8 的适用范围。

### 9.1 2 页 vs 4 块不矛盾：它们不是同一套实现

| 维度 | 我们逆向抓包的（NacreHis 那套） | 本 SDK（LCRFRW_SDK + 演示程序） |
|---|---|---|
| 程序 | `NacreHis.exe` → `SmartLock` → `SM_RW_Card` | `RWCardDemo.exe` / 二次开发调用 |
| Hook 点 | `LC32RFRW.dll` 的 `WriteFile`（**底层串口帧**） | — |
| 写卡命令 | `setuppwm` + **`writepwm`**（T5557/5567，`te_*`） | **`em4305_login_asc` + `em4305_write`**（EM4305） |
| 写几页 | **2 页**（页1、页2）——`docs/抓包样本与验证记录.md` §8 已记录 | **4 块 = 16 字节**（block 5..8）；版本 0 时 2 块 |
| 卡格式版本 | 由原厂软件内部决定 | `mif_selecom` 从 `LcSDK.ini` 读，默认 2；无 ini 才 3 |

**结论：抓到的 2 页是原厂门锁软件的真实行为，不是抓漏、也不是被截断。**

### 9.2 决定性证据：`dword_1002000C` 是 ini 里的可配置项【反编译】

```c
// mif_selecom（0x10003691）
Stream = fopen(FileName, Mode);
if ( Stream != nullptr )
{
    PrivateProfileIntA = GetPrivateProfileIntA(AppName, KeyName, 2, FileName);  // 默认 2
    if ( PrivateProfileIntA >= 4 )
        PrivateProfileIntA = 2;                     // ≥4 一律归 2
    dword_1002000C = PrivateProfileIntA;
}
else
{
    dword_1002000C = 3;                             // 连 ini 都没有才用 3
}
```

配合 `sub_1000C7B6` 的 `v12 = 4; if ( dword_1002000C == 0 ) v12 = 2;`：
**只有版本 = 0 才写 2 块**；版本 2 / 3 都写 4 块。而 `tem_writedoorcard13_sdk` 会把它设成 3。

所以「写几块」取决于**软件读到的 ini 版本号**，不是写死的。

### 9.3 现场卡是 TEMIC（T5557/5567），不是 EM4305 ⚠️

用户确认：**现场卡是 TEMIC 门锁卡**，我们的 `sdk/PMSLockSDK.cs` 走
`te_setuppwm_asc` + `te_writepwm_asc`（T5557/5567 命令集，**7 页 × 4 字节**）。

本 SDK 的 `LcSDK.ini` 是 `CardType=6` → `mif_selecard(6)` → **EM4305** 路径（**8 块 × 4 字节**）。

**这是 125 kHz 上两种不同的可读写芯片，页/块结构不同。** 因此：

- 我们抓到的「2 页」= T5557 的真实行为；
- §8 里「原厂写 4 块 = 16 字节」「`tfzd` 在 `v51[8]`」这些结论，**属于 EM4305 路径，不能直接套到现场 TEMIC 卡上**。

### 9.4 对 TD-142 / TD-144 的直接影响

`tfzd`（退房钟点）与 `fs`（开反锁）是 **EM4305 路径**的写卡参数。若现场卡是 T5557，需要先回答：

1. 这份 SDK 的 T5557 路径（`te_*`）写几页？`tfzd` / `fs` 是否也有对应位置？
2. 若没有 → 说明 **T5557 卡格式本身不带钟点/反锁字段**，TD-142 / TD-144 对现场卡不适用（除非换卡型或换芯片）。

→ 这个判断直接改变 TD-142 / TD-144 的前提，已同步进待办。

### 9.5 对 TD-140 的修正

原验证方案「用 `RWCardDemo.exe` 写卡」默认走 EM4305。现在必须改成：

| 步骤 | 内容 |
|---|---|
| **第 0 步** | **先确认这份 SDK 能驱动哪种卡**：查 `mif_selecard` 参数含义、`te_*` 与 `em4305_*` 的适用卡型；或用读卡器实测哪种命令能读到现场卡 |
| 第 1 步起 | 若 SDK 能驱动 T5557 → 用它写卡抓样本，验证 `tfzd`/`fs` 是否真的落进页/块；若不能 → 本 SDK 对本项目**只作语义参考**，`tfzd`/`fs` 在现场卡上无实际落点 |

### 9.6 一句话总结

> 我们抓的 2 页是 T5557 卡（现场卡）的真实行为；这份 SDK 默认用 EM4305（4 块 16 字节）。
> 两者的「卡格式」根本不是一回事，所以「为什么只有两页」的答案是：**原厂软件就是只写两页，
> 写四页的是另一个芯片的另一套 SDK。**
