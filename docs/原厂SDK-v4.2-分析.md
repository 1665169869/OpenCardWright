## 3. 参数语义（【原厂文档】原文要点）

| 参数 | 含义 | 取值范围与规则 |
|---|---|---|
| `BH` | 门锁编号 | **10 字符**，锁的唯一标识（不是房号） |
| `fksj` | 发卡时间 | 年月日时各两位，共 8 字符，例：`04080910` = 2004-08-09 10 时 |
| `xh` | 一小时内发卡序号 | **0–62**；超过 63 次则 `fksj` 小时 +1、序号从 0 重来 |
| `sjdw` | 时间单位 | **0=小时，1=天，2=月，3=年**；其它值按「天」 |
| `sjlength` | 时间长度 | 1–63 小时 / 1–63 天 / 1–15 月 / 1–3 年 |
| `gs` | 挂失标志 | 1 = 取消在用的客人卡（挂失），0 = 不取消 |
| `tfzd` | **退房钟点** | **11–18**；例：13-01-01 08:00 写 1 天、钟点 13 → 有效期到 13-01-02 13:00 |
| `fs` / `OpenInner` | **是否允许开反锁** | 0 = 不允许，1 = 允许 |
| `p_nLockAP` | 系统标识号 | 二级代理商模式才有效，其它填 0；对应 `LockID.ini` 最后的 `LockAP=` |

**关键规则（原厂原文）**

1. 「卡中作业流水号必须**大于等于**门锁电路板中作业流水号，否则开门失败」——
   与我们实测的「大于→开并更新、**等于→开**、小于→拒」**完全吻合**【实测印证】。
2. 「作业流水号 = 日期时间中的年月日时 + 1 小时内所发卡的序号」——**流水号带时间戳**，
   不是纯递增计数器。
3. 多客人同房：**第一张卡挂失标志置 1，后两张置 0**（同一房间最多 3 张）。
4. **退房回收卡**（原文）：「客人退房时仍可调用此函数…此时 `BH`=实际门锁编号，
   `fksj=00000000, xh=0, sjdw=0, sjlength=1, gs=0` 即实现退房回收卡片功能」。
5. 钟点房的退房时间不受 `tfzd` 限制，`tfzd` 填 11–18 任意值即可。
6. 授权：未授权读写卡返回 **128**；用非专用接口读卡器返回 **129**。
7. 总卡 / 栋卡 / 层卡：**同一个写卡函数**，只换 `BH`（门锁编号）。
8. `LockID.ini` 由 `GetLockID.exe` 从原厂门锁软件工作目录导出：左边房号、右边门锁编号，
   末行 `LockAP=X`。

## 4. 与现有实现的对比

### 4.1 已完全印证的部分（我们的逆向结论正确）

| 我们的结论 | 原厂文档 | 状态 |
|---|---|---|
| 锁按「房间 × 卡型」记高水位，大于→开并更新、等于→开、小于→拒 | 「作业流水号必须 ≥ 锁内值」 | ✅ 一致 |
| 卡内 16 位序号（`5B EC` 后两字节）| 「作业流水号」 | ✅ 同一概念 |
| 同房多卡有特殊标志位 | 「多客人同房第一张挂失标志置 1」 | ✅ 解释了我们观察到的现象 |
| `config_parameter(0)` 明文模式 | `config_parameter` 导出 + 我们实测 | ✅ 一致 |
| EM4305 底层读写 | `em4305_*` 全套导出 | ✅ 一致 |

### 4.2 我们缺失 / 不同的部分（**重点**）

| # | 原厂能力 | 我们的实现 | 影响 |
|---|---|---|---|
| 1 | **退房钟点写在卡里**（`tfzd`，11–18） | 只存数据库算 `expires_at`（TD-126），卡里不写 | **锁不知道退房钟点**；我们之前认为「卡里只有时长码」可能不完整——页2 第 4 字节 `AB` 是否为钟点/标志编码，**需重新核查**【待验证】 |
| 2 | **开反锁标志**（`fs`/`OpenInner`） | 完全没有 | 新能力，可能需要新增卡型参数 |
| 3 | **时间单位支持月/年**（`sjdw` 0/1/2/3） | 只有天/小时；月/年用固定天数档位近似（90/120/360/1095） | 1095 天 ≈ 3 年但非精确月年 |
| 4 | **序号按「小时内 0–62」分段**（超 63 则小时 +1） | 全局单调递增计数器（`CardNo.state`） | 我们不复位，锁只比大小，实测可用；但与原厂流水号规则不同 |
| 5 | **流水号含发卡时间戳**（`fksj` 8 字符） | 序号无时间信息 | 影响「作业流水号存挡」的对账能力 |
| 6 | **退房回收卡用特定参数组合**（`fksj=00000000, xh=0, sjdw=0, sjlength=1, gs=0`） | 用全零 raw（`--p1 00000000 --p2 00000000`） | **字节可能不等价**：原厂 `sjlength=1, sjdw=0` 意味着时长码非零【待验证】 |
| 7 | 授权机制（128/129 错误码） | 无（我们的 CLI 直接调驱动） | 原厂 SDK 有授权限制，我们的方案绕过了 |

### 4.3 对我们最有价值的三条

1. **页2 第 4 字节（我们记作 `AB`）很可能是 `tfzd`/`fs` 的编码位**——若成立，我们的卡在
   「退房钟点非 12 点」时可能与锁的理解不一致。**建议用原厂 `RWCardDemo.exe` 写一张
   退房钟点 13 点的卡，与我们的卡逐字节比对**【待验证】。
2. **退房回收卡的官方参数**说明「全零」可能不是正确写法（原厂 `sjlength=1`），
   需要用原厂演示程序写一张回收卡抓字节验证【待验证】。
3. **`tem_writedoorcard13WithRec_sdk`** 说明原厂写卡时**同时写一条记录**（可能是卡内或软件侧），
   与我们「issuance 表只追加」的思路一致，但卡内是否有记录区未知【待验证】。

## 5. 结论

- 原厂这套 SDK 是**授权 + 门锁编号**模式（`BH` 是 10 字符门锁编号，不是房号），
  与我们「房号 → 序号」的方案是两套编码体系；**不能直接替换** `sdk/PMSLockSDK.cs`。
- 但它是**权威语义来源**：`tfzd`、`fs`、`sjdw`、`gs`、`xh` 五个参数解释了我们逆不出来的部分。
- 我们与它在「高水位」判定上完全一致，说明核心机制无误。
- 待验证项集中在**卡内字节的钟点/反锁/挂失编码**——需要用原厂 `RWCardDemo.exe` 抓样本。

## 7. IDA 反编译进展（2026-11-08，ida-mcp）

对 `LCRFRV_SDK.dll` 反编译了写卡链路，**确认了 `tfzd` 与 `fs` 的编码方式**（不再依赖猜测）：

### 7.1 调用链

```c
// 0x1000cade
tem_writedoorcard13_sdk(Src, a2, xh, sjdw, sjlength, gs, LockAP, tfzd, fs)
{
    byte_1001FED4   = fs;      // 开反锁 → 全局 1 字节
    dword_1001FED8  = tfzd;    // 退房钟点 → 全局 4 字节
    dword_1002000C  = 3;       // 卡格式版本标记
    return tem_writedoorcard_sdk(...);   // 基础版：把 tfzd/fs 从全局取用
}

// 0x1000853e → 0x10008885（真正的字节构造，9191 字符反编译体）
tem_writedoorcard_sdk → sub_10008885(Src, fksj, xh, sjdw, sjlength, gs)
```

`dword_1001FED8`（tfzd）的引用点：`sub_10008885`（0x10009153）、`tem_writedoorcard13WithRec_sdk`、
`Lc_writedoorcard13_sdk`。
`byte_1001FED4`（fs）的引用点：`sub_10008885`（0x1000933c）等。

### 7.2 `tfzd`（退房钟点）的编码【IDA 反编译】

```c
v17 = dword_1001FED8 - 11;                    // tfzd - 11
if ( dword_1001FED8 - 11 < 0 || v17 > 7 )
    v17 = 1;                                   // 越界（不在 11..18）→ 取 1（即 12 点）
...
sub_10002E3C(v17, KeyName, 3);                 // 转成 3 位二进制串（'0'/'1'）
sub_10002ABD(KeyName, KeyName);                // 反转
memcpy((char *)&v27[2] + 5, KeyName, 3u);      // 写进位串工作区 offset 21..23
```

**结论：`tfzd` 不是整字节，而是「`tfzd - 11` 的 3 位二进制」**（11→000, 12→001, … 18→111），
越界值一律按 `1`（12 点）处理。**3 位正好覆盖 8 个钟点，与文档「11~18」完全吻合。**

### 7.3 `fs`（开反锁）的编码【IDA 反编译】

```c
memcpy((char *)&v27[1] + 4, a1_0, 1);            // offset 12 = '1'
if ( byte_1001FED4 != 0 )
    memcpy((char *)&v27[1] + 5, a1_1, 1);        // fs≠0 → '1'
else
    memcpy((char *)&v27[1] + 5, a0_2, 1);        // fs=0  → '0'
memcpy((char *)&v27[1] + 6, a0_3, 1);            // offset 14 = '0'
memcpy((char *)&v27[1] + 7, a0_4, 1);            // offset 15 = '0'
```

常量实测值：`a0_1/a0_2/a0_3/a0_4 = '0'`，`a1_0/a1_1 = '1'`（`.rdata` 逐字节读取）。

**结论：`fs` 是位串里的 1 个 bit（offset 13）**，紧邻三个固定位（'1','0','0'）。

### 7.4 底层拼字节的机制【IDA 反编译】

- `sub_10002E3C(v, buf, n)` = **整数 → n 位二进制字符串**（低位先出，不足左补 '0'）
- `sub_10002ABD(s, dst)` = **字符串反转**（因为上一步是低位先出）
- `sub_10002767(s)` = **二进制串 → 整数**（从串尾读，串尾 = bit0 / LSB）

所以原厂是「**按位拼一张 32 位的表，再解析成 4 字节**」——这与我们逆向出的
`页1 = 5B EC | ((序号&0x0F)<<4 | 低4) | (序号>>4)`、`页2 = 时长码|卡号低|卡号高|AB`
这种「位段拼接」结构**同源**，但**字段顺序与位宽不同**。

### 7.5 已经能下的结论

1. 我们的卡**没有写 `tfzd` 与 `fs`** —— 已从代码层面证实（不是猜测）。
2. `AB`（页2 第 4 字节）**不是**钟点字段：`tfzd` 是 3 位、`fs` 是 1 位，都在 32 位位串的中段，
   跨字节分布，与「整字节 AB」不对应。
3. 原厂的位串布局与我们不同（原厂把 `tm_hour/tm_mday/tm_mon/tm_wday/年` 也塞进位串，
   那是**「作业流水号含时间戳」**的实现；我们是纯 16 位序号）。
