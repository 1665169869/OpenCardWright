# 发卡/写卡 调用链逆向（主程序 → 驱动）

> 目标：搞清"原厂软件发卡时到底调用了哪些接口"。
> 方法：模块字符串交叉验证 + IDA 反编译 + 串口抓包对拍。
> 结论：**业务数据由 `SmartLock.dll` 组装，实际写卡由 `SM_RW_Card.dll` 的 `DoWriteCard` 完成，
> 最终落到 `LC32RFRW.dll` 的 `te_*` 底层函数。**

---

## 1. 模块调用链

```
NacreHis.exe                      主程序（MFC，86 KB）
  │  内含字符串：SmartLock、ModuleSelect、DoSmartLockDlg      【实测】
  ├─ ModuleSelect.dll             模块选择器
  │  内含字符串：SmartLock、ModuleSelect                      【实测】
  └─ SmartLock.dll                门锁业务模块（3.74 MB，唯一导出 DoSmartLockDlg）
      │  内含全部 11 个 Do* 名字 + "SM_RW_Card"               【实测】
      └─ SM_RW_Card.dll           读写卡引擎（180 KB，12 个导出）
          │  内含 te_*/mif_*/em4305_* 名字并全部 GetProcAddress 【实测】
          └─ LC32RFRW.dll         读卡器驱动（92 个导出）
              └─ CH340 串口 → 发卡器 → TEMIC 卡
```

> 三个上层模块都用 `LoadLibraryA` + `GetProcAddress` 动态解析下一层，
> 因此**没有静态导入表**可查，只能靠字符串 + 反编译定位（本文件就是这样做的）。

`DoWriteCard` 从对象 `+0x0C` 取卡型索引，跳转到对应实现：

| 索引 | 卡型 | 写卡实现 | 读卡实现 |
|---|---|---|---|
| 0 | IC | `sub_100126AB` | `sub_1000FFE6` |

| **2** | **TEMIC** | **`sub_10011DEB`** ★ | `sub_1000FBB1` + `sub_1000F72D` |
| 3 | M1 | `sub_10010F2E` | `sub_1000EEE3` |
| 4 | EM | `sub_100118A6` | `sub_1000F72D` + `sub_1000FBB1` |

## 4. TEMIC 写卡实现 `sub_10011DEB`（核心）

### 4.1 入参

`__thiscall`：`this` = 驱动对象（内含函数表、串口参数、密码串），`a2` = 请求结构：

| 偏移 | 内容 |
|---|---|
| `a2+4` | 起始页索引（0 基） |
| `a2+8` | 页数 |
| `a2+12` … `a2+32` | **6 个 CString**：每页 4 字节的十六进制串（"5BEC3100" 这种） |

约束：`起始页 + 页数 ≤ 6`，否则返回 **8**（页范围非法）。

### 4.2 执行序列（反编译逐句对照）

```
mif_selecom(obj->port, obj->baud)          // 表偏移 +296
  失败 → mif_closecom(); return 1
Sleep(100)
mif_shake()                                 // +300
  if (shake != 0):
      config_parameter( devtype==31 ? 0 : 3 )   // +404，★ 扰码开关在这里决定
      mif_shake()
      sub_1001BE1F(obj)                     // 内部复位/清缓冲
      mif_shake()
  仍失败 → mif_closecom(); return 204
mif_selecard(5)                             // +308（5 = TEMIC）
  失败 → mif_closecom(); return 201
te_read_asc(buf)                            // +340
  失败 → mif_closecom(); return 202
[CString::Right(buf, 2) → sub_10005B75 解析尾部状态字节]
[与页数比较，决定起始页/页数是否需要修正]
te_setuppwm_asc(0, 页数, 0, 1, obj->password)   // +332
  失败 → mif_closecom(); return 206
for attempt in 0..2:                        // 最多重试 3 轮
    for page in 起..起+页数-1:
        te_writepwm_asc(0, page+1, 页数据hex, obj->password)   // +356
    Sleep(obj->delay)
    te_read_asc(buf)                        // +340 回读
    if (回读 == 期望) break
if 仍不匹配:  sub_100190E2(...) ; mif_closecom() ; return 10
else:         mif_beep(obj->beepTimes) ; mif_closecom() ; return 0
```

### 4.3 与抓包的逐条对照

| 反编译里的调用 | 抓到的帧 |
|---|---|
| `mif_selecom` | （不开串口，无帧） |
| `config_parameter(0)` | `80 00 0000A500 DA` |
| `mif_shake()` | `80 05 5555AAAA 7C` |
| `mif_selecard(5)` | `80 02 05 78` |
| `te_read_asc` | `80 15 6A` |
| `te_setuppwm_asc(0,2,0,1,pwd)` | `80 17 00 12000206 0610011A 1D` |
| `te_writepwm_asc(0,1,pwd,data)` | `80 17 01 12000206 <data> cs` |

**完全一致** —— 说明我们复刻的时序就是原厂时序，不是"差不多"。

## 5. TEMIC 读卡实现 `sub_1000FBB1`

与写卡同一套开场：

```
先把 6 个输出缓冲填空串（strcpy(a2[i+3], "")）

```

## 6. 密码从哪来

- `SM_RW_Card.dll` 内部**没有** `"12000206"` 字面量（已全文件搜索）。
- 密码是对象成员（`this + 40` 的 CString），由调用方（SmartLock）在初始化时传入。
- **`SmartLock.dll` 数据段内含字面量 `"12000206"`**（文件偏移 `0x328C78`，已全二进制搜索确认）。
- 数据库 `Xt_cs` 里没有这个值（已全库检索）。

**结论：TEMIC 写密码是硬编码在 `SmartLock.dll` 里的 `12000206`**，不是配置项。
换现场/换版本时如果这个值变了，需要重新抓包确认。

## 8. 实测：直接调用厂商 `DoWriteCard`（成功）

### 8.1 结论先说

`SM_RW_Card.DoInitPara` + `DoWriteCard` **可以被外部进程直接调用并发卡成功**，
但前提是初始化结构体必须逐字节对齐（`+28` 有一个保留字段，见 8.3）。

| 尝试 | 结果 | 说明 |
|---|---|---|
| 结构体按"6 指针连续"构造 | `DoInitPara` 返回 **13** | 字符串全部错位，校验失败 |
| 绕过门闩后调 `DoWriteCard` | 返回 **10**，卡不变 | 密码槽拿到的是 12 个 0 → 线上密码 `00000000` |
| **补齐 `+28` 后** | **`DoInitPara -> 0`，`DoWriteCard -> 0`** | **✅ 卡内字节与请求完全一致** |

### 8.2 两个结构体（反编译 + 实测）

**`DoInitPara(void *p)`** —— `p` 共 **52 字节**：

| 偏移 | 类型 | 含义 |
|---|---|---|
| +0 | int | 设备类型（0~5，用于 `DoCheckDeviceEnv` 分派） |
| +4 | int | 串口索引（0=COM1） |
| +8 | int | 波特率（必须 ∈ {1200,2400,4800,9600,19200,38400,76800,115200}） |
| +12 | int | 蜂鸣标志（==1 才响） |
| +16 | int | 蜂鸣次数（1~250） |
| +20 | byte | 标志字节 |
| +24 | char* | 字符串 1（长度 6，十六进制） |
| **+28** | **int** | **保留字段（DLL 不使用，但必须占位，否则后面全部错位）** |
| +32 | char* | **写密码**（现场 `12000206`） |
| +36 | char* | 字符串 3（长度 12） |
| +40 | char* | 字符串 4（长度 12） |
| +44 | char* | 字符串 5（长度 6） |
| +48 | char* | 字符串 6（长度 6） |

**`DoWriteCard(void *p)`** —— `p` 共 36 字节：

| 偏移 | 类型 | 含义 |
|---|---|---|
| +4 | int | 起始页（0 基，对应卡页 1） |
| +8 | int | 页数（起始+页数 ≤ 6） |
| +12 … +32 | char* ×6 | 每页 4 字节的 HEX 字符串（8 个字符） |

> 两者都是 `__cdecl`，**调用者不需要传 `this`** —— 导出内部写死
> `mov ecx, offset unk_100284E8`（全局单例）。

### 8.3 根因：结构体少一个 4 字节字段，整体错位

`DoInitPara` 的参数结构实际是 **52 字节**，字符串指针在 `+24, +32, +36, +40, +44, +48`
—— **`+24` 和 `+32` 之间空了一个 4 字节字段（`+28`，DLL 不使用但占位）**。

反编译依据（`sub_1000D4C4`）：

```c
v62[9]  = *(char**)(a2 + 24);   // obj+36
v62[10] = *(char**)(a2 + 32);   // obj+40  ← 密码
v62[11] = *(char**)(a2 + 36);   // obj+44
v62[12] = *(char**)(a2 + 40);   // obj+48
v62[13] = *(char**)(a2 + 44);   // obj+52
v62[14] = *(char**)(a2 + 48);   // obj+56
```

如果按"6 个指针连续排列"（24,28,32,36,40,44）去构造，密码就会落到 `+28`，
DLL 读 `+32` 时拿到的是第 3 个字符串 → **密码变成 12 个 0 的前 4 位**，
且 6 位校验串全部错位 → `DoInitPara` 返回 13。

修正后实测：

```
DoInitPara -> 0            ← 完全通过，不需要任何绕过
obj+36 = "000000"       obj+40 = "12000206"   ← 密码正确落位
obj+44 = "000000000000" obj+48 = "000000000000"
obj+52 = "000000"       obj+56 = "000000"
```

> 教训：MFC/C++ 的 `__thiscall` 结构体不能靠"看几个赋值语句"猜布局，
> 必须按反编译里的实际偏移逐个对齐。

### 8.4 `config_parameter(0)/ (3)` 由 `obj[2]` 决定

`obj[2] == 31` 才用明文 `(0)`，否则 `(3)`（扰码）。
`obj[2]` 来自 `Config.ini` 的 `[LockCard] ComEncryptFlag`（默认 0），
`--patch31` 可把 `obj+8` 改成 31。

**实测：两种模式都能正确写卡**（卡内字节均与请求一致）。

> ⚠️ **但要注意遗留状态**：用过 `config_parameter(3)` 之后，**读卡器会停留在扰码模式**。
> 此时再用明文模式（`config(0)`）的工具去读，会得到
> `mif_shake -> 2`（无卡）、`te_read -> 5`（空），**看起来像卡坏了，其实不是**。
>
> 复位方法：调一次 `config_parameter(0)`（我们的 `IssueCardByRoom` / `PMSLockSDK`
> 开头都会调），或拔插读卡器。
>
> **建议**：写卡统一走 `config_parameter(0)`（`--patch31`，或把 `Config.ini` 的
> `[LockCard] ComEncryptFlag` 设成 31），避免留下扰码状态影响后续工具。

### 8.7 失败→成功的排查过程（供参考）

| 阶段 | 现象 | 原因 |
|---|---|---|
| 1 | `DoInitPara -> 13`，`DoWriteCard -> 7` | 结构体少 `+28` 字段 → 6 个字符串全部错位 |
| 2 | 绕过门闩后 `DoWriteCard -> 10` | 密码槽读到的其实是第 3 个字符串（12 个 0）→ 线上密码 `00000000` |
| 3 | 抓包看到 `01 00000000 5BECF100` | 同上，密码传空 |
| 4 | 补齐 `+28` 后 `DoInitPara -> 0` | ✅ 全部校验自然通过 |

> 期间还发现：`te_setuppwm` 是否发送由 `v63` 决定，`v63` 只在
> "卡上已有页数 < 请求页数" 或 `sub_1001C470()==0` 时置位。
> 在成功用例里 `DoInitPara` 返回 0 后该条件自然满足，无需额外干预。

### 8.8 定论

| 方案 | 能否发卡 | 说明 |
|---|---|---|
| **厂商 `DoWriteCard`（外部调用）** | **✅ 可以** | 结构体对齐正确后，`DoInitPara -> 0`、`DoWriteCard -> 0`，卡内字节与请求一致 |
| 我们的 `PMSLockSDK` | ✅ 可以 | 时序完整，不依赖厂商 DLL，跨版本更稳 |

**两者都能用，区别在于**：

| 维度 | 厂商 `DoWriteCard` | 我们的 `PMSLockSDK` |
|---|---|---|
| 依赖 | `SM_RW_Card.dll` + `IOServer` 目录 + `Config.ini` | 只要 `LC32RFRW.dll` |
| 数据组装 | 仍需自己做（它只写页） | 内置卡格式与房号表 |
| 32/64 位 | 必须 32 位进程 | 必须 32 位进程 |
| 版本风险 | 厂商换实现就失效 | 只依赖驱动导出 |
| 卡号管理 | 需自备 | 内置计数器 |

> **结论：本仓库只保留自研 SDK 这一套实现**，不提供厂商 `DoWriteCard` 的调用工具。
> 上面的对比仅用于说明"为什么不走厂商接口"，以及记录那段逆向过程。

## 9. 对第三方的意义

1. **不走厂商业务层**：`SM_RW_Card` 的 12 个导出是"厂商业务层"，
   入参结构、对象布局、错误码都是私有约定，必须先 `DoInitPara`（否则返回 7），
   且结构体差 4 字节就整体错位（本文档第 8 节完整记录了这个坑）。
2. **直接调驱动**：`LC32RFRW.dll` 的 `te_*` 是无状态的 C 导出，
   参数就是页号/数据/密码，没有对象和初始化门闩。
3. **数据组装自己做**：原厂是在 `SmartLock.dll` 里把房号/天数/卡号拼成 8 字节的，
   这段逻辑我们已经完全还原（见技术规格第 4 节）。
