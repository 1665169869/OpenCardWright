# TD-219 真机复核：客卡与总控卡的小时编码是否真的存在「+1」差异

**优先级** P0 · **状态** 待办 · **来源** US-1110-1 · **模块** 发卡与卡片

**为什么做**：用户判断「按程序逻辑来讲，客卡与总控卡的时长编码不可能存在 +1 差距，需要测试」。
现有实现与文档都按「客卡 `0x40 | (小时+1)`、总控卡 `0x40 | 小时`」写，
依据是 **2026-11-05 的原厂抓包**，不是从程序逻辑推导出来的。若这个结论是样本误读，
现有 `DurationHours()` 会给客卡多发一小时，属于发卡格式错误，必须先复核再谈其他管理卡字段。

**现状**【核实】：

| 位置 | 现状 |
|---|---|
| `sdk/PMSLockSDK.cs::DurationHours(int hours, bool guest)` | `v = guest ? hours + 1 : hours`，`>63` 截到 63，返回 `0x40 \| (v & 0x3F)` |
| `CardBuilder.BuildGuestHour(...)` | 传 `guest: true` → 1 小时写 `0x42` |
| `CardBuilder.BuildMaster(days, hours, ...)` | `hours > 0` 时传 `guest: false` → 1 小时写 `0x41` |
| `selftest` 客卡向量 | 1h→`42`、3h→`44`、6h→`47`、62h→`7F`（`PMSLockCard.cs` 的 `Vectors`） |
| `selftest` 总控向量 | 2h→`42`、3h→`43` |
| `docs/TEMIC门锁卡技术规格.md` §5.2 | 表：1h 总控 `41` / 客卡 `42`；2h `42` / `43`；3h `43` / `44`；日租两者相同 |
| `docs/抓包样本与验证记录.md` §7 | 原厂软件发总控卡：1h→`41 C1 2B AB`、2h→`42 C2 2B AB`、3h→`43 C3 2B AB` |
| `docs/抓包样本与验证记录.md` §1 | 原厂软件发客卡：1h→`42 8A 22 AB`、3h→`44 89 22 AB`、6h→`47 8B 22 AB`、62h→`7F 8C 22 AB` |

两套抓包来自**同一天、同一台读卡器、同一版原厂软件**，样本本身互相独立，但目前只各取了一组，
没有做过「同参数客卡 vs 总控卡」的对照实验，也没有用 `RWCardDemo` 或真锁闭环。

**测试方案（四路交叉，任一不一致即视为推翻）**

1. **原厂软件对照**：用同一张空白卡，分别发 1 / 2 / 3 小时的客卡与总控卡，
   读回 `raw_hex`，只比 `页2[0]`；同一温度、同一读卡器，避免样本漂移。
   判据：客卡 1h 是 `42` 还是 `41`。
2. **`RWCardDemo` 交叉验证**：若其卡型下拉支持写客卡/时钟卡，用同样的「时间单位 = 小时、长度 = 1」
   各写一张，对比 `页2[0]`；同时记下 demo 算出的到期时刻。
3. **本 SDK 对照**：`PMSLockCard.exe issue --type guest/hour/master --hours 1` 各发一张，
   逐字节对比；只用于确认「我们写了什么」，不用于证明锁怎么解释。
4. **真锁闭环**：用 1 小时客卡与 1 小时总控卡各刷一次门，按 `RWCardDemo` 算出的到期时刻
   核对实际失效时间。若客卡实际有效 2 小时，说明 +1 错误；若 1 小时，说明 +1 是退房宽限。

**判定与后续**

- 若复核确认客卡 `0x42`、总控 `0x41`：条目标「已复核」，把本表证据补进
  `抓包样本与验证记录.md`，并在技术规格 §5.2 去掉「待复核」标记。
- 若发现客卡也应是 `0x41`：`DurationHours()` 的 `guest` 分支错误，需同步改
  `CardBuilder`、`selftest` 向量（客卡小时向量）、技术规格 §4.3/§5.2、抓包样本表，
  并重发受影响卡型；此时另开一条修复条目，不并入本条。
- 若两者都表现异常（例如客卡比总控多 1、但都不是 ±1 的简单关系）：先登记新样本，
  再重新推导小时段编码，不要直接改代码。
