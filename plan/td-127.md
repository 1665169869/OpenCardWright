# TD-127 同房第二张卡复用有效首卡序号（客人要两张卡）

**优先级** P1 · **状态** 已完成· **来源** US-1106-28 · **模块** 发卡与卡片

**为什么做**：部分客人需要**两张门禁卡**。但锁按「房间 × 卡型」的**序号高水位**判定（大于→开并更新，等于→开，小于→拒）——同房再发一张卡（卡号递增）会把高水位顶高，**第一张仍在有效期内的卡立即被锁拒开**；同时锁是从首次刷卡起算有效期，新卡首刷还会干扰原有计时的可预期性。`room.max_cards` 只是数据库里的业务上限，**锁侧没有这个概念**。

**现状**【本轮已核实】：
- 锁的高水位判定与「日租 / 钟点两套高水位互不影响」见 AGENTS §5；发第二张卡 = 卡号递增 = 顶掉第一张。
- `ocw_store::latest_active_guest_card`（lib.rs:499）已能取该房最新有效客卡（口径与 `count_active_cards` 一致）——复用判定可以直接复用这个函数。
- CLI 支持 `--serial` 指定卡号构包（`sdk/PMSLockCard.cs:69`）；现有发卡路径每卡消耗一个新卡号（`CardNoPolicy::Increment`，由 `CardNo.state` 推进）。
- `checkout_card(card_no)` 按**卡号**退房（`commands.rs:2000`）——同号两条记录的退房语义需核实。

**需求**：该房存在**仍在有效期内**的第一张客卡 且 未超 `room.max_cards` → 新卡**复用第一张卡的卡号**构包并入库（同号两条 `issuance` 记录，**不消耗 `CardNo.state`**）；否则走现有递增。

**改动点（方向）**
1. 发卡命令（`issue_guest`）写库前查 `latest_active_guest_card(room)`：命中有效首卡 且 `count_active_cards < max_cards` → 构包传 `--serial <首卡卡号>`、issuance 记录复用同号；未命中或超限 → 现有递增路径。
2. `expires_at`：第二张卡按**本次发卡**独立计算（TD-126 算法，退房日 + 钟点）——不回改第一张。
3. UI 不变（发卡流程照旧）；记录页会出现两条同卡号记录，需确认展示不混淆（卡号历史展开已按 issuance id 区分）。

**验收标准**
- [ ] 同房首卡有效期内再发 → 两张卡**卡号相同**、第一张真机仍能开门（现场验证）
- [ ] 无有效首卡或已超 `max_cards` → 走现有递增 / 拒发逻辑不变
- [ ] 退房、到期提醒、记录页展示按拍板落地，行为明确
- [ ] `cargo test --workspace` + `pnpm exec tsc --noEmit` 全绿

**依赖 / 风险**：锁对「相同卡号 = 高水位相等」的**具体行为未实测**（等于→开；是否更新时长/重置首刷计时待真机验证）——复用前必须现场确认；复用**不推进 `CardNo.state`**（与「不要跳号」原则兼容，反而更省号）；同号退房/按卡号查询的语义要先核实 SQL。
