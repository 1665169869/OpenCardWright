# TD-212 BUG：退房后未写入退房数据（含非本系统卡）

**优先级** P1 · **状态** 已完成 · **来源** US-1109-5 · **模块** 房间与预订

**为什么做**：用户反馈退房后没有写入退房数据，怀疑与「这张卡不是本系统发出的」有关；
但用户明确认为**非本系统卡也不应该出现“退房成功但没有任何退房数据”**的结果。

## 现状（登记时）

当前后端有两条退房路径：

1. **正常持卡退房**：`checkout_card`
   - 先校验卡型、卡号、房号，然后**先擦卡**（`device.erase_card()`），
   - 再用卡号时间戳 `find_issuance_by_stamp` 反查记录；
   - 如果本地没有记录，返回「没有找到这张卡的发卡记录」，但此时卡可能已经被擦掉。
   - 这条路径可能表现为：卡被擦了，但数据库/审计没有对应的退房记录。

2. **非本系统卡强制退房**：`force_checkout_card`
   - 只调用 `checkout_room` 关闭该房全部有效卡并改房态；
   - **没有读写卡逻辑**，不会把退房数据写入卡内，也不会擦卡；
   - 前端 `CheckoutCardModal` 文案写的是「直接写入退房数据」，与实际行为不一致。

## 改动点

- [x] 正常持卡退房改成「**先查记录，后擦卡**」：查不到记录时不要先擦卡。
      —— `commands.rs` 起先做 raw/时间戳匹配，匹配不到直接报错返回，擦卡在其后；
      注释明写「避免 TD-212 的『先擦后查失败』」。
- [x] 非本系统卡强制退房明确语义：**二次确认后擦成空白卡**（全零 8 字节）+ 关闭该房有效卡 + 改房态。
      `force_checkout_card(room_no, erase)` 在关库之前调 `device.erase_card()`；
      擦卡失败不阻断退房，结果与审计都记录原因。
- [x] `CheckoutCardModal` 的按钮结果、成功提示和错误提示与实际行为一致：
      二次确认列表写明「关闭全部有效卡 / 把卡擦成空白卡 / 改房态 / 记审计」，
      结果按 `erased` 输出「卡已擦成空白卡」或「未擦卡（原因）」。
- [x] 审计记录补充：卡号、记录 id、是否写卡、失败原因。
      —— `checkout_card` 成功带 `id=` / `cardNo=` / `erased=` / `matchedBy=`；
      卡型不符、卡片无房号、匹配不到记录、擦卡失败都写 `failed` 审计；
      `force_checkout_card` 记 `cardsClosed=` / `foreignCard=true` / `erased=` / `eraseError=`。
- [x] 非本系统卡不再静默成功：读卡退房匹配不到记录即报错；强制退房必须先过二次确认，
      并明确告知会不会擦卡、擦没擦成。

## 完成形态（2026-11-10）

- `CheckoutResult` 增加 `erased: bool` / `erase_error: Option<String>`；换房与无卡退房固定 `false`（不碰读卡器）。
- 前端 `api.ts::forceCheckoutCard(roomNo, erase = true)` 透传；`CheckoutCardModal` 结果提示区分三种情况。
- 已知限制：擦卡仍是**全零 8 字节**，与原厂「退房回收卡」（`sjlength=1`）是否等价**仍待实测**，
  由 TD-143 跟踪；擦卡失败时旧卡仍可能开门，前端已明确提示。

## 验收标准

- [x] 正常卡退房：`issuance.checked_out_at` 写入，卡擦成空白卡，审计可查（含记录 id 与是否擦卡）。
- [x] 非本系统卡退房：不再出现“提示成功但没有任何退房数据”；擦卡与库记录结果都有明确反馈。
- [x] 查不到发卡记录时，不会在报错前不可逆地擦掉卡 —— 匹配在擦卡之前，失败即返回并落失败审计。
- [x] 卡型/房号不匹配、卡片无房号等错误路径不产生误导性成功提示 —— 各自有独立文案与失败审计。

## 待拍板

已定（2026-11-10 用户拍板）：非本系统卡退房**二次确认后擦成空白卡**（而非只关库、也非写专门退房数据）；
真正的「退房回收卡」字节差异由 TD-143 实测后再决定是否升级。
