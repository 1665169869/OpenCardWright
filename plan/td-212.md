# TD-212 BUG：退房后未写入退房数据（含非本系统卡）

**优先级** P1 · **状态** 待办 · **来源** US-1109-5 · **模块** 房间与预订

**为什么做**：用户反馈退房后没有写入退房数据，怀疑与「这张卡不是本系统发出的」有关；
但用户明确认为**非本系统卡也不应该出现“退房成功但没有任何退房数据”**的结果。

## 现状（需先复现确认）

当前后端有两条退房路径：

1. **正常持卡退房**：`checkout_card`（`app/src-tauri/src/commands.rs`）
   - 先校验卡型、卡号、房号，然后**先擦卡**（`device.erase_card()`，约 2102–2115），
   - 再用卡号时间戳 `find_issuance_by_stamp` 反查记录；
   - 如果本地没有记录，返回「没有找到这张卡的发卡记录」，但此时卡可能已经被擦掉。
   - 这条路径可能表现为：卡被擦了，但数据库/审计没有对应的退房记录。

2. **非本系统卡强制退房**：`force_checkout_card`（约 2166–2199）
   - 只调用 `checkout_room` 关闭该房全部有效卡并改房态；
   - **没有读写卡逻辑**，不会把退房数据写入卡内，也不会擦卡；
   - 前端 `CheckoutCardModal` 文案写的是「直接写入退房数据」，与实际行为可能不一致。

需要先确认用户说的「退房数据」指：
- 数据库 `issuance.checked_out_at` / 房态 / 审计记录，还是
- 卡内字节（擦成空白卡 / 写退房标记）。

## 改动点（建议）

- [ ] 复现并记录：正常卡、非本系统卡、卡号时间戳对不上、卡片无房号四种场景，分别看
      数据库 `issuance`、`audit`、卡内回读结果。
- [ ] 正常持卡退房改成「**先查记录，后擦卡**」：查不到记录时不要先擦卡；
      或擦卡失败/查记录失败时给出明确回滚说明。
- [ ] 非本系统卡强制退房明确语义：
      - 若产品要求写卡：在二次确认后擦卡/写退房数据，并把写卡结果返回前端；
      - 若产品只写数据库：修改文案为「关闭房间有效卡并改房态」，不要宣称写卡。
- [ ] `CheckoutCardModal` 的按钮结果、成功提示和错误提示与实际写卡行为一致。
- [ ] 审计记录补充：是否写卡、卡号、记录 id、失败原因。
- [ ] 若卡不是本系统发出，至少不能静默成功；应提示「本机无发卡记录，已按房间退房，未写卡」或执行用户确认后的写卡。

## 验收标准

- [ ] 正常卡退房：`issuance.checked_out_at` 写入，卡按约定擦除/写退房数据，审计可查。
- [ ] 非本系统卡退房：不会出现“提示成功但没有任何退房数据”的情况；写卡与库记录结果都有明确反馈。
- [ ] 查不到发卡记录时，不会在报错前不可逆地擦掉卡（或明确告知已擦卡并提供补救）。
- [ ] 卡型/房号不匹配、卡片无房号等错误路径不产生误导性成功提示。
