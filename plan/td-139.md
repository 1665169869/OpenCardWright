# TD-139 原厂 SDK 开发模块 V4.2_D 解压与分析

**优先级** P1 · **状态** 已完成 · **来源** US-1106-41 · **模块** 发卡与卡片

**为什么做**：用户从原厂拿到 `125K SDK开发模块(RF)_V4.2_D`，其中带**官方接口文档**——
这是比逆向更权威的语义来源，能解释我们之前只能靠实测推断的部分。

**处理**
1. 用 `7z` 解压到 `vendor/125k-sdk-v4.2/`（6 目录 / 55 文件 / 9.5 MB），原始 rar 一并保留；
   清理了重复解压目录，Word 提取文本另存为 `RF门锁接口说明V4.2_D-提取文本.txt`（Word 97 格式，
   用 Python 提取 `WordDocument` 流，word-mcp 不可用）。
2. 文档通读 + `dumpbin /EXPORTS`（99 个导出，编译时间 2016-01-08）+ Delphi/VB 接口声明交叉核对。
3. 产出 `docs/原厂SDK-v4.2-分析.md`：包结构、接口清单、参数语义、与现有实现的逐项对比。

**关键结论**
- **完全印证**我们的核心结论：「作业流水号必须 ≥ 锁内值」= 我们实测的「大于→开并更新、等于→开、小于→拒」；
  「多客人同房第一张卡的挂失标志置 1」解释了我们观察到的同房多卡现象。
- **新信息**：`tfzd`（退房钟点 11–18）与 `fs`（是否开反锁）是**写卡参数**，`sjdw` 支持 0=小时 / 1=天 /
  2=月 / 3=年；`xh` 是「一小时内序号 0–62」，超 63 要把 `fksj` 小时 +1 并复位——与我们「全局递增计数器」不同。
- **原厂退房回收卡参数**：`fksj=00000000, xh=0, sjdw=0, sjlength=1, gs=0`（注意 `sjlength=1` 不是 0），
  与我们用全零 raw 擦卡可能**字节不等价**。
- 原厂 SDK 走「10 字符门锁编号 `BH` + 授权」体系（未授权返回 128、非专用读卡器 129），
  与我们的「房号 → 序号」是两套编码，**不能直接替换** `sdk/PMSLockSDK.cs`。
- 文档未提但 DLL 里有的函数：`tem_writedoorcard13WithRec_sdk`（带记录写卡）、`tem_readrfcardall_sdk`、
  `tem_readtimercard_sdk`/`tem_writetimercard_sdk`（计时卡）。
