# TD-224 入住登记表单两个 BUG（打开看不到历史 / 关单后多出空白住客）

**优先级** P1 · **状态** 已完成 · **来源** US-1111-2 · **模块** 房间与预订

**为什么做**：TD-220 上线后前台反馈两个问题：
① 打开「入住登记」看不到之前登记过的住客；
② 添加一名住客后点「关闭登记单」，会多出一条空白住客记录。

## 现状与根因【核实】

**① 打开看不到已登记信息**
- `CheckinForm` 打开时（`app/src/components/CheckinForm.tsx:97-114`）调 `start(roomNo)` →
  `api.createCheckin(roomNo)`。
- 后端 `create_checkin`（`ocw-store`）逻辑是「同房有 `open` 单则复用，**没有就新建一张空单**」。
- 因此房间上次已关单时，再打开会新建空单，历史住客看不到。

**② 关闭登记单多出一条空白住客**
- 前端只有 `addGuest` 做了「姓名或证件号至少一项」校验；`readAndAdd` 等路径没有。
- 后端 `add_checkin_guest`（`ocw-store`）**只校验登记单是否 `open`**，不校验内容。
- `emptyGuest()` 返回 `{ idType: '身份证' }`，所以一条「只有证件类型」的记录也能落库。
- 具体触发路径待复现，三种可疑：
  1. 「添加住客」与 Modal footer 的「关闭登记单」按钮位置接近，点击误触；
  2. `closeCheckin` 后 `onSaved` 触发的刷新链路里又调了一次 `addCheckinGuest`；
  3. `readIdCard()` 返回空/部分字段时仍被追加。

## 改动点

1. **打开时优先加载已有单**：
   - 先 `api.getOpenCheckin(roomNo)`；
   - 有 `open` 单 → 加载它（现状）；
   - 没有 → `api.listCheckins({ roomNo, pageSize: 1 })` 取最近一张历史单，**只读展示**，
     顶部提示「该房最近一张登记单已关闭」并给「开新单」按钮，点后才 `createCheckin`；
   - 两者都没有 → 保持现状（新建空单）。
2. **后端补空校验**：`add_checkin_guest` 增加「`name` 或 `id_number` 至少一项非空」，返回可读错误；
   `update_checkin_guest` 同样校验，避免把唯一住客改成空。
3. **前端防误触**：`addGuest` 按钮 `disabled={busy}`；「关闭登记单」改受控 `Popconfirm` 二次确认；
   `readAndAdd` 在 `info` 无任何可用字段时直接报错、不调用 `addCheckinGuest`。
4. **先复现 ② 再定最终修法**：按上面三种路径逐条复现，确认是哪一条，再补回归。

## 验收标准

- [ ] 房间有 `open` 单时打开表单，能看到该单全部住客，可编辑 / 删除
- [ ] 房间只有已关闭的历史单时，打开先只读展示历史（含住客），点「开新单」才建新单
- [ ] 后端拒绝空白住客（单测：姓名与证件号都空 → `Err`）
- [ ] 添加住客后点「关闭登记单」，住客数量不变（不再新增空白行）
- [ ] 身份证读卡失败 / 空结果时不会写入住客
- [ ] `cargo test --workspace`、`pnpm exec tsc --noEmit`、`pnpm exec vite build` 通过

**① 打开看不到已登记信息** —— 已改：`CheckinForm` 新增 `bootstrap(roomNo, createIfNone)`，
按「本房 open 单 → 最近一张历史单（只读 + 提示 + 「开新单」按钮）→ 从未登记过才新建」加载。

**② 关单后多出空白住客** —— 三道防线：
- 后端 `GuestIdentity::has_identity()`（姓名或证件号 trim 后非空），
  `add_checkin_guest` / `update_checkin_guest` 均先校验并返回「住客至少要有姓名或证件号」；
- 前端 `readAndAdd` 读到空结果时直接报错、不调 `addCheckinGuest`；
- 「关闭登记单」改为 `Popconfirm` 二次确认，「添加住客」按钮 `disabled={!openState || busy}` 防重复提交。

**回归用例**：`checkin_rejects_blank_guest`（只有 idType / 全空格被拒；只有姓名可落库；
改成空白被拒且原资料保留）。
**复现说明**：三种可疑触发路径中，代码层面能确认的是「后端不校验 + `emptyGuest()` 自带 `idType`」
这条漏洞本身；前端误触路径已用二次确认与禁用兜住，现场再复现属验证而非阻塞。
