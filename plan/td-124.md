# TD-124 持卡退房时把卡写成空白卡（clear 状态）

**优先级** P1 · **状态** 已完成· **来源** US-1106-24 · **模块** 发卡与卡片

**为什么做**：持卡退房目前**只改数据库**（`checked_out_at`），卡内数据原封不动——锁仍然认这张卡，退房不等于卡作废。用户要求：持卡退房时把卡片数据写成 **clear（空白卡）**，让卡当场失效。

**现状**【核实】：
- `commands.rs` 的 `checkout_card`（约 2000 行）只 `UPDATE issuance` + `record_audit`，**全程无设备调用**；`ocw_store::checkout_room` 的注释也写明「门锁里的卡仍然有效，要让门锁立刻失效还需刷退房钟点卡」。
- SDK 能力盘点（2026-11-07 grep 实测）：
  - **读侧**：`CardBuilder.Parse` 对 28 字节全零判为 `CardKind.Blank`（「空白卡 / 已退房」）——退房后可读回验证；
  - **写侧**：CLI `issue --type clear` → `IssueClear`，写的是**清除卡**字节（`5BEC9BE5`…，技术规格 §5.3），**不是**空白卡；`issue --raw --p1 --p2` → `WriteRaw(p1, p2)` 可写任意页1/页2 —— 页3–7 原厂本就全零，把页1/页2 写成零即得 28 字节全零 = 空白卡；
  - **没有**现成的 `IssueBlank` / `WriteBlank` 命令。

**改动点（方向，待拍板后实施）**
1. 擦卡路径二选一（见「待拍板」）：A = `WriteRaw("00000000","00000000")` 零写（不动 `sdk/`）；B = SDK 新增语义化 `IssueBlank`。
2. `checkout_card` / `force_checkout_card` 写库成功后调用擦卡；`OCW_SIM` 模拟设备跳过（构包器无擦卡语义）。
3. 擦卡失败语义：库已标退房但卡未擦 → 明确提示「退房已登记但擦卡失败，请重试」，并可读卡验证（`Blank` 即成功）。
4. 擦卡前沿用现有 `pre_read_card` 模式（先读卡确认在位）。

**验收标准**
- [ ] 持卡退房后读卡返回空白卡（28 字节全零 / 解析为 `Blank`）
- [ ] 擦卡失败有明确提示与重试路径，库与卡状态不长期不一致
- [ ] 模拟设备（`OCW_SIM`）跳过擦卡，退房流程不受影响
- [ ] `selftest` 27/27 + `cargo test` + `pnpm exec tsc --noEmit` 通过（若走 B 动了 `sdk/`，必须先 selftest 全绿）

**依赖 / 风险**：写零卡**不可逆**（原卡数据抹除，但退房语义本就是要作废，可接受）；驱动写卡走 `te_setuppwm_asc`/`te_writepwm_asc`，写后回读可能拿到旧值（`WriteAndVerify` 已有重试）；**动 `sdk/` 需用户批准**（AGENTS §9）。
