# TD-214 BUG：已满房退一张后房态仍为已满房

**优先级** P1 · **状态** 待办 · **来源** US-1109-7 · **模块** 房间与预订

**为什么做**：房间发了两张客卡后房态变成「已满房」，退掉其中一张后仍显示「已满房」；
用户期望剩余有效卡未达上限时回退为「未满房」。

## 现状

- `ocw-store::checkout_issuance`（`app/src-tauri/crates/ocw-store/src/lib.rs:622`）只在
  `remaining == 0` 时把房态改成退房默认态（空脏）。
- `remaining > 0` 时完全不改房态，因此原本的 `occupied_full` 会一直保留。
- 发卡时 `commands.rs:1114-1126` 会按有效卡数把 `vacant_clean` / `reserved` / `occupied_partial`
  升到 `occupied_partial` 或 `occupied_full`；退房缺少对应的反向迁移。
- 状态 key（`schema.sql`）：
  - `occupied_partial` = 未满房
  - `occupied_full` = 已满房

## 改动点

- [ ] 退房后重算房态：
  - `remaining == 0`：保持现有逻辑，改为 `checkout_status`（默认空脏）。
  - `remaining > 0` 且当前状态是 `occupied_full`：回退为 `occupied_partial`。
  - `remaining > 0` 且当前状态是 `occupied_partial`：保持不变。
  - 维修 / 其他 / 空净 / 预定等人工状态不要被自动覆盖。
- [ ] 单卡退房 `checkout_issuance` 与批量退房 `checkout_room` 共用同一套重算逻辑，不能只修一条路径。
- [ ] 按 `effective_max_cards` 判断，不硬编码 2；房间配置上限 / 全局默认都要覆盖。
- [ ] 审计记录保留 remaining 与退房前后房态，便于现场排查。

## 验收标准

- [ ] 房间上限 2：发 2 张 → 已满房；退 1 张 → 未满房（剩余 1 张）。
- [ ] 再退最后 1 张 → 退房默认态（默认空脏），不是未满房。
- [ ] 上限 3：发 3 张 → 已满房；退 1 张 → 未满房。
- [ ] 上限 1：发 1 张 → 已满房；退最后 1 张 → 退房默认态。
- [ ] 房间处于维修/其他人工状态时，退房不擅自改成未满房。
- [ ] 批量退房与单卡退房结果一致。
- [ ] 增加结账后房态迁移单测；`cargo test --workspace` 通过。
