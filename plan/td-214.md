# TD-214 BUG：已满房退一张后房态仍为已满房

**优先级** P1 · **状态** 已完成 · **来源** US-1109-7 · **模块** 房间与预订

**为什么做**：房间发了两张客卡后房态变成「已满房」，退掉其中一张后仍显示「已满房」；
用户期望剩余有效卡未达上限时回退为「未满房」。

## 现状（登记时）

- `ocw-store::checkout_issuance` 只在 `remaining == 0` 时把房态改成退房默认态（空脏）。
- `remaining > 0` 时完全不改房态，因此原本的 `occupied_full` 会一直保留。
- 发卡时 `commands.rs` 会按有效卡数把 `vacant_clean` / `reserved` / `occupied_partial`
  升到 `occupied_partial` 或 `occupied_full`；退房缺少对应的反向迁移。
- 状态 key（`schema.sql`）：`occupied_partial` = 未满房、`occupied_full` = 已满房。

## 改动点

- [x] 退房后重算房态：
  - `remaining == 0`：转 `checkout_status`（默认空脏）。
  - `remaining > 0` 且当前状态是 `occupied_full`：回退 `occupied_partial`。
  - `remaining > 0` 且当前状态是 `occupied_partial`：保持不变。
  - 维修 / 其他等人工状态不被自动覆盖。
- [x] 单卡退房 `checkout_issuance` 与批量退房 `checkout_room` 共用同一套重算逻辑。
- [x] 按 `effective_max_cards` 判断，不硬编码 2（回退只看 `occupied_full` 这一个状态，天然与上限无关）。
- [ ] 审计记录保留 remaining 与退房前后房态 —— `remaining` 已在 `checkout_card` 审计里（TD-212 顺带补了记录 id），
      「退房前房态」未单独落审计；现场排查可用 `room.status` 当前值 + 房间日志。

## 完成形态（2026-11-10）

- `checkout_issuance`：`find_room` 取当前房态；`maintenance` / `other` 视为人工态不覆盖；
  `remaining == 0 && !manual` → `dirty_status`；`remaining > 0 && status == occupied_full` → `occupied_partial`。
- `checkout_room`：批量关闭后同样跳过 `maintenance` / `other`。
- 单测：`checkout_downgrades_full_room_to_partial`、`checkout_keeps_manual_room_status`。

## 验收标准

- [x] 房间上限 2：发 2 张 → 已满房；退 1 张 → 未满房（剩余 1 张）—— 单测 `checkout_downgrades_full_room_to_partial`。
- [x] 再退最后 1 张 → 退房默认态（默认空脏），不是未满房 —— 同上。
- [x] 上限 3 / 上限 1 同理 —— 回退只依赖 `occupied_full` 状态，与上限值无关。
- [x] 房间处于维修/其他人工状态时，退房不擅自改成未满房 —— 单测 `checkout_keeps_manual_room_status`。
- [x] 批量退房与单卡退房结果一致 —— 两条路径都有同一套判断。
- [x] 增加结账后房态迁移单测；`cargo test --workspace` 通过。

## 待拍板
