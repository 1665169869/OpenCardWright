# TD-144 「开反锁」能力（`fs` / `OpenInner`）

**优先级** P2 · **状态** 不排期· **来源** US-1106-42 · **模块** 发卡与卡片

> **结论（2026-11-08）**：`fs` 在**页4**（EM4305 路径），T5557 写不进；且卡号低字节 bit5 已改作
> 「时」的低位（TD-150），不再有冲突。本条改为不排期。

**结论（2026-11-08 实测）：`fs` 位于卡数据 `BYTE9`（页3[1]）的 bit5，页3 同样写不进 → 现场卡不适用；
另需注意若按另一种切分它落在「卡号低字节 bit5」，卡号递增到 bit5=1 的段是否被误判仍需真机验证。**

**为什么做**：原厂写卡函数有 `fs`（0 = 不允许开反锁、1 = 允许），我们**完全没有这个参数**。
若现场存在「客房内反锁后仍需要开门」的场景（常见于连住客人），这是能力缺口。

**现状**【核实】：`fs` 是位串里 1 个 bit（offset 13），见 `docs/原厂SDK-v4.2-分析.md` §7.3；
我们的 `CardBuilder` 不接收该参数。

**改动方向（待拍板后才动）**
1. 先确认业务是否真需要（问现场：反锁后开门是常规需求还是异常操作）；
2. 若需要：`CardBuilder` 加参数 + 发卡表单加「允许开反锁」勾选 + 写卡字节；
3. 真锁验证。

**验收标准**
- [ ] 需求结论明确（做 / 不做）
- [ ] 若做：开反锁 0/1 的卡字节差异与预期一致，真锁行为符合预期

**依赖 / 风险**：**需要修改 `sdk/`（只读约束）**，并影响 27 条黄金向量；UI 也要加交互。
**待拍板**：**是否要做这个功能**（以及是否允许改 `sdk/`）。建议默认：**暂不做**，先记档，等现场提出需求。
前置提醒：`fs` 同属 **EM4305 路径**参数；T5557 卡是否有对应位，取决于 TD-140 第 0 步的结论。
