## 1. 产品定位

### 1.1 一句话

给中小宾馆/公寓前台用的**开源发卡台**：读卡、发卡、管卡号、留记录。
原厂软件已停止维护，本产品接管"发卡"这一个高风险环节，其余交给用户已有的流程（纸单/Excel/现有 PMS）。

### 1.2 目标用户

| 角色 | 场景 | 关键诉求 |
|---|---|---|
| 前台 | 客人到店，递卡 | 3 步内出卡，不能出错，不能重复发号 |
| 店长/管理员 | 新锁上线、丢卡、维护 | 管理卡（复位/清除/安装/校时）有护栏，操作留痕 |
| 集成商 | 给客户部署 | 装得上、离线可用、出问题能导出诊断包 |

### 1.3 范围（In / Out 显式清单）

**In（v1 必做）**

1. 读卡并解析（卡型、房号、天数/小时、卡号、原始 8 字节）
2. 发客卡：日租（1–1095 天）、钟点（1–62 小时）
3. 发管理卡：总控、复位、清除、安装、退房钟点、校时（均带二次确认）
4. 卡号治理：顺序分配、状态文件对齐、水位预警、回绕阻断
5. 发卡记录与审计日志（谁、何时、给哪个房、什么卡型、什么卡号、结果）
6. 房号表管理（导入 `RoomIndex.ini` / CSV，房号 ↔ 卡内序号）
7. 设备诊断：端口探测、驱动指纹（SHA-256）、`selftest` 自检、诊断包导出
8. 安装包 + 首次启动向导 + 中文文档

**Out（v1 明确不做）**

| 不做 | 原因 |
|---|---|
| 房态、入住登记、账务、报表 | 属 PMS 范畴，做了就是半个 PMS，工期与维护面失控 |
| 挂失卡、应急码卡、楼栋/楼层/应急/通道卡 | SDK 无格式（无样本），不臆造 |
| 修改 `sdk/` 任何文件、重编 SDK 二进制 | 老板已设硬约束 |
| 多门店/云端同步 | v1 单机本地；接口留白留给 v2 |
| 手机 App、小程序 | 无必要，Web 已可适配平板 |
| 自动刷卡开门测试 | 需要额外硬件治具，非软件范畴 |

### 1.4 与 SDK 的边界（架构级硬约束）

```
Keyloom （本产品，AGPL-3.0 开源）
   │  只通过「命令行 + JSON」契约调用
   ▼
PMSLockCard.exe （既有产物，x86，.NET FW 4.0，不修改）
   │
   ▼
LC32RFRW.dll + 125kHz 读卡器
```

这条边界的意义：**卡格式知识与驱动适配全部留在闭源侧**，开源仓库里不出现 8 字节格式、不出现厂商 DLL。既降低法务暴露，也让社区贡献者无需接触硬件即可开发（用模拟设备）。

## 3. 技术选型

### 3.1 首选方案

| 层 | 选型 | 版本基线 | 理由 |
|---|---|---|---|
| 运行时 | .NET 10（LTS） | 10.0.x | 2025-11-11 发布，支持至 **2028-11-14**；.NET 8 于 **2026-11-10** 就 EOL（5 天后），不能做新项目基线 |
| 后端 | ASP.NET Core Minimal API | 随 .NET 10 | 端点少（~12 个），无需 MVC 全栈；AOT 友好、单文件发布 |
| 设备通道 | 子进程 + `--json` | 既有 CLI | 零改动复用 SDK；崩溃隔离；驱动可替换 |
| ORM | EF Core + SQLite | EF 10 / SQLite 3.4x | 单机单用户，无需服务端数据库；WAL 模式足够 |
| 前端 | React + TypeScript | React 19.3 / TS 5.9 | 19.3.0 于 2026-09-09 发布，为当前稳定线 |
| 构建 | Vite | 8.x | 2026-08 已到 8.2.x |
| 组件库 | Ant Design | 6.x | 6.x 已适配 React 19；中文后台表单/表格/日期选择开箱可用 |
| 数据请求 | TanStack Query | 5.x | 发卡是"命令式 + 需刷新"的典型场景 |
| 测试 | xUnit + Playwright + Vitest | — | 注意：**不用 FluentAssertions 8+**（已转商业许可），改用 xUnit 原生断言或 Shouldly（BSD） |
| 打包 | Inno Setup 6 | — | 中文安装界面成熟、脚本简单、体积小 |
| CI | GitHub Actions（windows-latest） | — | 与 GitHub 开源托管天然一体 |

### 3.2 反选论证（为何不选其它）

| 备选 | 不采用的原因 |
|---|---|
| **WPF / WinForms 桌面单进程** | 老板已选本地 Web。另：单进程意味着 UI 崩溃=设备句柄悬空；Web 形态前台平板可直接用。 |
| **Electron 壳** | 包体 150MB+，主进程仍需拉起 x86 设备进程，复杂度不降反升；安全面（Node 集成、远程内容）更大。 |
| **Tauri 壳** | 需引入 Rust 第二技术栈，社区贡献门槛高；解决不了 32 位设备访问，仍要 sidecar。 |
| **后端直接引用 `PMSLockSDK.dll`（net40）** | .NET 10 无法可靠加载 net40 程序集；退回 net48 则失去 EF Core 10 / Minimal API，且 EF Core 3.1 已 EOL。代价换不来收益。 |
| **在 .NET 10 里 P/Invoke `LC32RFRW.dll` 直连** | 要重写 `te_*` 封装、绕开 `CardBuilder` 分层，违背"字节只在 CardBuilder"的既有纪律；驱动版本极敏感（结论只对单一 SHA-256 成立），升级即返工。 |
| **MySQL / PostgreSQL** | 单机 < 10 万条记录，引入服务端数据库只增加部署负担。 |
| **Vue 3** | 生态同样成熟，但 React 的 OSS 贡献者池更大；差异不构成决策依据，若老板团队更熟 Vue 可替换，架构不受影响（BFF 已隔离）。 |

### 3.3 选型验证清单

| 验证项 | 状态 | 说明 |
|---|---|---|
| 可行性：子进程调用 CLI 完成一次发卡 | **未验证（P0 前置）** | M0 第一天用 `PMSLockCard.exe read --json` 打通，记录耗时 |
| 兼容性：Win10/11 x64 运行 x86 子进程 | 高置信 | WOW64 天然支持；需验证串口驱动在多会话下的表现 |
| 依赖：.NET 10 SDK / Node 24 / pnpm 10 | 需确认 | 本机 Node 为 22.22.2，Vite 8 需 ≥ Node 20，可运行；CI 固定版本 |
| 性能：单张卡端到端耗时 | **待实测** | 验收阈值：P95 ≤ 3s（含串口打开、写、回读校验） |
| 安全：本地 HTTP 面 | 设计已缓解 | 仅绑定 127.0.0.1、随机端口 + 一次性令牌、无跨域、无外网回连 |

## 4. 架构设计

### 4.1 进程与分层

```
┌──────────────────────────────────────────────┐
│ 浏览器（React SPA，由 Agent 托管静态文件）      │
└───────────────┬──────────────────────────────┘
                │ HTTP 127.0.0.1:<随机端口> + Bearer
┌───────────────▼──────────────────────────────┐
│ Keyloom.Agent  (.NET 10, win-x64, 托盘/服务)  │
│  ├ Api        端点、鉴权、幂等                  │
│  ├ Application 发卡用例、事务边界               │
│  ├ Domain     卡号分配、卡型规则、护栏           │
│  ├ Data       EF Core + SQLite（WAL，单写入）   │
│  └ Device     IDeviceGateway                   │
│      ├ CliDeviceGateway  → 子进程 PMSLockCard   │
│      └ SimDeviceGateway  → 黄金样本回放（CI 用）│
└───────────────┬──────────────────────────────┘
                │ Process.Start（x86）
        %ProgramData%\Keyloom\sdk\PMSLockCard.exe
```

**要点**

- `sdk/` 在安装时复制到 `%ProgramData%\Keyloom\sdk\`，**运行时只写这份副本**；仓库内的 `sdk/` 保持只读。
- 单写入者：只允许一个 Agent 实例持有设备（命名互斥量 `Global\Keyloom.Device`），并发请求排队而非并行。
- 所有设备操作串行化，超时 15s，失败自动重试 0 次（避免重复写卡），返回结构化错误码。

### 4.2 设备通道契约（本产品自有的稳定接口）

内部接口 `IDeviceGateway`：

```csharp
Task<DeviceProbe> ProbeAsync(CancellationToken ct);              // 端口/驱动指纹/自检
Task<CardSnapshot> ReadAsync(CancellationToken ct);              // 读卡
Task<IssuedCard> IssueAsync(IssueRequest req, CancellationToken ct);
Task<SelfTestResult> SelfTestAsync(CancellationToken ct);        // 转发 selftest
```

`CliDeviceGateway` 的实现规则：

1. 参数全量显式传入（`--ini`、`--port`、`--json`），**不依赖工作目录**
2. 解析 stdout 的 JSON；非 0 退出码映射为领域错误（沿用 SDK 的 0–7 语义）
3. 超时杀进程树；stderr 全文入诊断日志（脱敏后）
4. 每次调用后记录 `duration_ms` 与退出码，供"设备健康"页展示

> 这一层的价值：将来 SDK 换成 COM 直连、或换读卡器型号，只改一个实现类。

### 4.3 数据模型（SQLite）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `room` | `room_no` PK, `room_index` UQ, `building`, `floor`, `room_type`, `active` | 房号 ↔ 序号，来自 `RoomIndex.ini` |
| `issuance` | `id`, `uuid` UQ, `room_no`, `kind`, `days`, `hours`, `card_no`, `raw_hex`, `operator_id`, `device_id`, `result`, `error_code`, `idempotency_key` UQ, `created_at` | 发卡流水，**只追加** |
| `operator` | `id`, `login` UQ, `display_name`, `role`, `pwd_hash`, `active` | 角色：`admin` / `frontdesk` |
| `audit_log` | `id`, `at`, `operator_id`, `action`, `target`, `detail`, `result` | 管理卡、改配置、导入房号必留痕 |
| `card_seq` | `id`, `last_no`, `updated_at` | 本地序列（与 `CardNo.state` 对齐） |
| `device` | `id`, `reader_id`, `port`, `driver_sha256`, `first_seen`, `last_seen` | 换机器/换驱动可追溯 |
| `setting` | `key`, `value` | 端口、驱动目录、卡号策略等 |

**不做**：客人身份信息表（v1 无入住业务）。发卡记录只存"给哪个房、什么卡"，符合 SDK 文档"身份信息不写卡"的既有边界。

### 4.4 卡号治理（本项目最危险的领域逻辑）

卡号是 16 位、全局单调、锁端按"房间 × 卡型"维护高水位。错一次 = 全楼卡失效。设计如下：

| 规则 | 实现 |
|---|---|
| 默认分配 | 由 CLI 自增（`CardNo.state` 是唯一分配器），Agent 只记录返回值 |
| 指定号码 | 仅管理员"补卡/重发"时允许，需输入原因，落审计 |
| 启动自检 | 读取 `CardNo.state`，与最近一条 `issuance.card_no` 比较；偏差 > 0 时**告警并禁止发卡**，要求人工确认 |
| 水位预警 | `≥ 0xE000` 黄色横幅；`≥ 0xFF00` 红色阻断，仅允许管理卡 |
| 回绕 | **不自动回绕**。到 `0xFFFF` 停止发卡，引导走"复位作业向导"（空房时段、逐锁刷复位卡） |
| 1095 天卡 | 二次确认弹窗，明确写出"会把该房间高水位推到 3 年后" |

### 4.5 API（v1 契约草案）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/login` | 返回短期 token（内存态，重启失效） |
| GET | `/api/health` | Agent 版本、设备状态、驱动指纹、自检结果 |
| GET | `/api/rooms` / POST `/api/rooms/import` | 房号列表 / 导入（ini、csv） |
| POST | `/api/device/probe` | 端口探测（等价 `ports`） |
| POST | `/api/cards/read` | 读卡 |
| POST | `/api/cards/issue` | 发客卡（需 `idempotencyKey`） |
| POST | `/api/cards/admin` | 发管理卡（需 `confirm: true` + 角色 admin） |
| GET | `/api/issuances` | 分页查询流水 |
| GET | `/api/cardnos/status` | 水位与预警 |
| POST | `/api/diagnostics/bundle` | 导出诊断包（日志 + 配置去密） |

约定：所有写操作幂等键 24h 有效；错误统一 `{code, message, hint}`；`code` 沿用 SDK 语义并扩 `K1001` 起的应用层码。

### 4.6 安全设计

| 面 | 措施 |
|---|---|
| 网络暴露 | 仅 `127.0.0.1`，端口随机；启动时把带令牌的 URL 写入仅当前用户可读的文件并自动打开浏览器 |
| 鉴权 | 本地账号，Argon2id（或 PBKDF2-SHA256 ≥ 210k 迭代）哈希；无默认口令，首启强制设置 |
| 权限 | `admin` 才能发管理卡、改配置、导入房号；`frontdesk` 只能发客卡与读卡 |
| 卡密码 | `12000206` 存于 `%ProgramData%` 配置，**不入库不入库仓**；诊断包导出时脱敏 |
| 供应链 | 前端 `pnpm-lock.yaml`、后端 `packages.lock.json` 锁定；CI 跑 `dotnet list package --vulnerable` 与 `pnpm audit` |
| 审计 | 管理卡操作不可删除，导出时带完整性哈希 |

## 5. 开源与法务

| 项 | 结论 |
|---|---|
| 许可证 | **AGPL-3.0**（老板已选）。含义：任何人改后对外提供服务也必须开源；酒店自用不受影响 |
| 商用边界 | 卖部署/实施/定制可以，卖闭源分支不行。若未来要做 SaaS，须先评估 AGPL 网络条款 |
| 贡献协议 | DCO（Developer Certificate of Origin），不引入 CLA，降低贡献摩擦 |
| **厂商二进制** | `LC32RFRW.dll` 无授权、原厂已倒闭，**不可随仓库/安装包分发**。安装器提供"导入向导"：让用户指向自己机器上的原软件目录，校验 SHA-256 `F2F4…BC0` 后复制到运行目录 |
| 逆向文档 | 留在本私有仓库；公开仓库只描述"CLI JSON 契约"，不描述卡内 8 字节格式 |
| 免责声明 | README 顶部显著位置：门锁属人身/财产安全设备，误发卡可能把客人锁在门外；复位卡、安装卡、清除卡须由培训过的管理员操作 |
| 名称合规 | 不含厂商商标；`TEMIC` 仅以"支持的卡片类型"出现于兼容性说明 |

## 6. 交付阶段（不含工时估算，排期由老板定）

1. 现场实测：本产品写出的一张卡，在真锁上开门成功（沿用 README 第八节同口径）
2. `selftest` 在健康页显示 27 通过 0 失败
3. 断网可用（拔网线全流程无失败）
4. 发卡端到端 P95 ≤ 3s（实测数据入文档，未达标则记录原因）
5. 安装包内不含任何厂商二进制

## 7. 风险登记

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | 厂商 DLL 再分发被追责（权属不清） | 中 | 高（下架/索赔） | 不分发；导入向导 + 哈希校验；README 声明 |
| R2 | 卡号状态双源不一致（DB vs `CardNo.state`） | 中 | 高（全楼卡失效） | 以 `CardNo.state` 为唯一分配器；启动强校验；偏差即阻断 |
| R3 | 串口被原软件/其它程序占用 | 高 | 中 | 启动预检 + 明确文案（"先关闭 NacreHis.exe"）；失败即诊断包 |
| R4 | 驱动版本漂移（结论只对单一 SHA-256 成立） | 中 | 高 | 登记驱动指纹；不匹配时页面显红并禁止发卡 |
| R5 | 子进程调用延迟影响体验 | 中 | 低 | 首次实测；必要时改为常驻小宿主（net48 x86）承载设备 |
| R6 | 复位卡/安装卡误操作导致锁"未安装" | 低 | 高（现场停业） | 管理员权限 + 二次确认 + 明确警示文案 + 操作前强制导出当前配置 |
| R7 | AGPL 吓退集成商 | 中 | 中 | README 写清"卖服务可以，卖闭源分支不行"；提供商业授权联系入口（后续决策） |
| R8 | 单人维护导致项目停滞 | 中 | 中 | 模拟设备 + 契约测试降低贡献门槛；文档优先于功能 |
