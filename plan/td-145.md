# TD-145 月/年时间单位精度

**优先级** P2 · **状态** 已完成 · **来源** US-1106-42 · **模块** 发卡与卡片

**为什么做**：原厂 `sjdw` 支持 0=小时 / 1=天 / **2=月 / 3=年**（1–15 月、1–3 年）；我们只有天/小时，
月/年用固定天数近似（90 / 120 / 360 / 1095 天）。其中 **1095 天 ≈ 3 年但差闰年**（3 年 = 1095 或 1096 天），
长有效期卡在年末签发时可能差一天。

**现状**【核实】：`sdk/CardBuilder` 的时长码为 `0x80 | 天数`（1–63）与 `0xC0 | round(天数/31)`（>63）；
`rules.rs` 的固定档位是 90/120/360/1095。原厂参数表见 `docs/原厂SDK-v4.2-分析.md` §3。

**2026-11-08 实测（关键证据）**：用原厂 SDK 按「时间单位 = 4（月）、长度 = 4」写卡，卡内得到 `0xC4`，
`RWCardDemo` 算出结束时间 **2027-03-04**（起始 2026-11-04）—— **正好 +4 个日历月**，不是 +124 天。

**所以低 6 位是「月数」，锁按月历加法执行**。我们的档位换算因此有实际偏差：

| 档位 | 我们写入 | 锁实际给 | 偏差 |
|---|---|---|---|
| 90 天 | `0xC3`（3 月） | 11-04 → **02-04 = 92 天** | **+2 天** |
| 120 天 | `0xC4`（4 月） | 11-04 → 03-04 = 120 天 | 0 |
| 360 天 | `0xCC`（12 月） | +12 个日历月 | 0（闰年除外） |
| **1095 天** | `0xE3`（35 月） | **35 个日历月 ≈ 1065 天** | **−30 天** |

**1095 天档位偏差最大（少了约一个月）**——对「3 年长住卡」是实质影响。

**改动方向**
1. 核算 90/120/360/1095 天与原厂「月/年」单位的实际差异（含闰年）；
2. 评估是否需要在文档里说明「档位是天数近似」；
3. 若差异影响业务（如 1095 天卡在 2 月签发），再讨论是否改用月单位。
