# TD-119 改房态二次确认：预定房先问是否取消今天的预定

**优先级** P2 · **状态** 已完成 · **来源** US-1106-19 · **模块** 房间与预订

**为什么做**：房态「预定」只反映当日预定（TD-202）；直接改房态会**静默丢掉今天的预定**（前台不知道取消了什么）。用户要求：修改房态时弹二次确认是否取消预定。

**现状**【核实】：`RoomManager.tsx` 的 `changeStatus`（单房抽屉）与 `applyBatchStatus`（多选批量）都直接 `api.setRoomStatus`，无任何确认；取消预定的 `api.cancelReservation` 已存在但无人调用。

**改动点**
1. 触发：目标房当前 `status === 'reserved'` 时先查 `listReservations(今天, 明天)`（覆盖今天）的 booked 预定，命中才弹框；纯未来预定（明天起）不返回、不弹框。
2. 确认框（受控 Modal，禁命令式）：单房文案含日期区间与姓名「{房号} 今天有预定：{区间}（{姓名}）。改为『{label}』将取消该预定，继续吗？」；批量列受影响房号「其中 N 间今天有预定（…），将一并取消」。
3. 「取消预定并改房态」（danger 主按钮）：`cancelTodaysReservations`（全量拉覆盖今天 → 过滤 booked → 逐条 `cancelReservation`）→ 再 `setRoomStatus` / `executeBatch`（批量循环）。
4. 「返回」与 X/ESC 只清状态，什么都不执行。
5. 模块级 `localDays()` 统一今天/明天计算；查询失败不阻断改房态（按原逻辑走）。

**验收标准**
- [x] 预定房（今天有预定）单房/批量改房态都先弹确认
- [x] 确认后先取消覆盖今天的 booked 预定再改房态
- [x] 「返回」不执行任何操作
- [x] 纯未来预定的房不弹框、不受影响
- [x] `pnpm exec tsc --noEmit` 通过；零 schema 改动、复用现有命令

**依赖 / 风险**：只动前端两入口；取消的是**覆盖今天**的预定（`listReservations(今天,明天)` 语义），明天起的预定保留；房态仍是人工字段。
**待拍板**：无（用户明确要求，触发条件与文案按用户描述实现）
