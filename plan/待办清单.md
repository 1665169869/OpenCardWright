## 4. 维护约定（每轮照做）

### 4.1 开工前

1. `git pull` 后确认文件头「基准」的 hash 与 `git log -2 --format=%h -- plan/待办清单.md` 的**第二行**对得上；
   对不上说明有人改过没更新头，先对齐。
   （不要拿 `git log -1` 比：`-1` 取到的是本次更新自己的提交，指针永远差一格 —— 这是早期版本的坑。）
2. 只在 §1 索引里挑条目；具体需求打开对应的 `td-xxx.md`，不要在旧正文里翻。

### 4.2 收工前（提交前必做）

| 情形 | 动作 |
|---|---|
| 整条做完 | 状态改 `已完成`；验收标准逐条打勾；`完成记录` 写 `日期 · 版本号 · <commit>`；摘要移入 `已完成.md`，详情留在/写入 `td-xxx.md`，从 §1 索引删除；CHANGELOG 新版本段写一句「修复：…（TD-xxx）」 |
| 做了一半 | 状态改 `进行中`；在 `td-xxx.md` 的「现状」末尾追加「已完成 X，剩 Y」；**不要新开条目** |
| 发现新需求 | 先查 §7 来源登记表；没有登记才新建 `td-xxx.md`（ID 取该模块当前最大号 +1），并在 §1 索引加一行 |
| 发现某条已过时 | 状态改 `已完成`，「完成记录」写「已被 TD-xxx 覆盖」，摘要移入 `已完成.md`，详情留在 `td-xxx.md`，不留悬空条目 |
| 用户拍板了某条 | 「待拍板」改成 `已定：…`，状态转 `待办`；同步删掉 §2 对应行 |
| 只改了文档 | 也要更新「最后更新」的 hash —— 这个字段是给下一个 agent 判断「条目还准不准」用的；同时同步总清单 / 已完成 / td 文件 |

### 4.3 硬规则

- **ID 永不复用**。做完的条目摘要移入 `已完成.md`，详情保留在 `td-xxx.md`，编号作废，新条目往后排。
- **一条待办只做一件事**。改动超过 5 个文件或跨两个模块，拆成两条。
- **不许无验收项**。「优化一下」「后续完善」这类不许进本文件。
- **不复制 CHANGELOG 全文**。来源只写 ID，正文只写「为什么 / 怎么做 / 怎么验」。
- **不写「定期回顾」**。回顾就发生在每次收工前的 4.2 表格里。

### 4.4 状态机

`待拍板` →（用户答复）→ `待办` → `进行中` → `已完成` → 归档。
唯一例外：`待办` 可直接跳 `已完成`（例如判定为「已被覆盖」）。
