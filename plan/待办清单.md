#### TD-104 长有效期卡（1095 天）发卡前确认词

**优先级** P1 · **状态** 已完成 · **来源** P8 · **模块** 发卡与卡片

**为什么做**：方案 §8 要求 1095 天卡「需输确认词，写明会把该房间有效卡顶到 3 年后」。现在只有一句
`长有效期卡会顶高该房间的水位` 的提示条（`src/components/IssueForm.tsx`），点一下就能发 —— 而**刷一次门就会把该房高水位顶到三年后**，
之后正常卡全废、只能用复位卡恢复（`AGENTS.md` §6）。

**现状**【核实】：`IssueForm` / `AdminCards` 均无确认词输入；`dayOptions` 里 90/120/…/1095 天档位可直接选中即发。

**改动点**
1. 前端：选中档位 > 63 天（`0xC0` 月码段）时，在发卡按钮旁要求输入固定确认词（如「顶高水位」），
   不填/填错保持按钮禁用，并在弹窗里列出该房当前有效卡与发卡后的预计水位。
2. 后端兜底：`issue_guest_card` / `issue_admin_card` 接收 `confirmLong: Option<String>`，
   档位进入月码段且确认词不符时返回 4xx（不信任前端）。
3. 审计详情里带上「长有效期卡确认词已输入」。

**验收标准**

#### TD-145 月/年时间单位精度

**优先级** P2 · **状态** 已完成 · **来源** US-1106-42 · **模块** 发卡与卡片

**为什么做**：原厂 `sjdw` 支持 0=小时 / 1=天 / **2=月 / 3=年**（1–15 月、1–3 年）；我们只有天/小时，
月/年用固定天数近似（90 / 120 / 360 / 1095 天）。其中 **1095 天 ≈ 3 年但差闰年**（3 年 = 1095 或 1096 天），
长有效期卡在年末签发时可能差一天。

**现状**【核实】：`sdk/CardBuilder` 的时长码为 `0x80 | 天数`（1–63）与 `0xC0 | round(天数/31)`（>63）；
`rules.rs` 的固定档位是 90/120/360/1095。原厂参数表见 `docs/原厂SDK-v4.2-分析.md` §3。

**2026-11-08 实测（关键证据）**：用原厂 SDK 按「时间单位 = 4（月）、长度 = 4」写卡，卡内得到 `0xC4`，
`RWCardDemo` 算出结束时间 **2027-03-04**（起始 2026-11-04）—— **正好 +4 个日历月**，不是 +124 天。

**所以低 6 位是「月数」，锁按月历加法执行**。我们的档位换算因此有实际偏差：

| 档位 | 我们写入 | 锁实际给 | 偏差 |
|---|---|---|---|
| 90 天 | `0xC3`（3 月） | 11-04 → **02-04 = 92 天** | **+2 天** |
| 120 天 | `0xC4`（4 月） | 11-04 → 03-04 = 120 天 | 0 |
| 360 天 | `0xCC`（12 月） | +12 个日历月 | 0（闰年除外） |
| **1095 天** | `0xE3`（35 月） | **35 个日历月 ≈ 1065 天** | **−30 天** |

**1095 天档位偏差最大（少了约一个月）**——对「3 年长住卡」是实质影响。

**改动方向**
1. 核算 90/120/360/1095 天与原厂「月/年」单位的实际差异（含闰年）；
2. 评估是否需要在文档里说明「档位是天数近似」；
3. 若差异影响业务（如 1095 天卡在 2 月签发），再讨论是否改用月单位。

**验收标准**
- [ ] 给出 4 个档位与原厂月/年单位的差异表

#### TD-150 CardNo 改为时间戳编码（日5 + 时5 + 序号6）

**优先级** P1 · **状态** 已完成 · **来源** US-1106-44 · **模块** 发卡与卡片

**为什么做**：原厂的「卡号」不是计数器，而是**紧凑时间戳**——`日(5位) + 时(5位) + 小时内序号(6位)`
正好 16 位。所以读卡器/原厂软件能从卡号还原真实发卡时间。我们的 `CardNo.state` 是纯递增，
解出来是「日 4 / 时 12 / 序号 6」这类假值，所以永远显示 2026-11-04。

**现状**【实测，6 组样本，见 `docs/TEMIC门锁卡技术规格.md` §4.4.2】

```
卡号高字节 = (日 << 3) | (时 >> 2)
卡号低字节 = ((时 & 3) << 6) | 小时内序号(0..63)

解码：日 = 高字节 >> 3
      时 = (高字节 & 0x07) * 4 + (低字节 >> 6)
      序号 = 低字节 & 0x3F
```

验证样本：`0x345B` → 日 11 / 时 12 / 序号 52；`0x345A` → 日 11 / 时 8 / 序号 52；
`0x2381` → 日 4 / 时 14 / 序号 1。全部与 RWCardDemo 读数一致。

**改动方向**
1. `CardNoStore.Next()` 改为按上面的公式生成卡号（输入：发卡时刻 + 该小时内已发张数）；
2. **保持全局单调递增**（锁的水位要求）：「日 + 时」本身递增，同小时内序号递增即可满足；
3. 跨小时/跨日时校验新值必须大于当前 `CardNo.state`，否则拒绝发卡并提示（避免倒退）；
4. `PMSLockCard.exe` 增加 `--at "YYYY-MM-DD HH"` 与 `--seq N`（**1–63，本小时第 n 张**），便于离线构包与 selftest 复核。
5. **进位后小时不回退**（2026-11-08 修正）：满 63 张进位到下一小时后，该「未来小时」成为下一次计算的基准；
   下一张接着在进位后的小时里发（第 65 张 = 15点第 2 张），不会退回当前小时。
   原实现用 `now > 卡号小时` 比较，第 65 张会算回当前小时——已修，并有 selftest 回归用例。

**验收标准**
- [ ] 按公式生成的卡号，RWCardDemo 读出的时间与发卡时刻一致（日/时/序号三项）
- [ ] 连续发 5 张卡，卡号严格递增
- [ ] 跨小时发卡，序号从 0 重新开始且卡号仍递增
- [ ] `selftest` 27 条向量仍全绿（现有向量的卡号需要同步重算或保留旧规则做兼容）

**依赖 / 风险**：
- **切换点风险最大**：新规则算出的卡号如果**小于**存量卡号，锁会当「旧卡」拒绝（需配复位卡或等自然增长到位）；
- 已有发卡记录（`issuance` 表）里的卡号是旧规则，混用后「按卡号排序」的历史会失真；
- 影响 27 条黄金向量（向量里写死了卡号）。

**切换流程（已定 2026-11-08：刷复位卡后统一切换）**
1. 停机窗口内，对**每个房间的锁各刷一次复位卡**（清空该房卡记录、水位归零）；刷完立刻收回复位卡（它不设防）
2. 切换后首次发卡，`CardNo.state` 会跳到 5 位数（如 `0x43C0`），属正常
3. 若 `Next()` 抛「卡号倒退」，说明该房还没刷复位卡 —— 补刷即可
4. 过渡期**不要混发旧卡**：旧卡号可能大于新卡号，锁会把它当成更新的卡
5. 已发出的旧卡在新规则下仍然可用，但读卡器解出的「发卡时间」会失真（旧号不是时间戳）

## 4. 维护约定（每轮照做）

### 4.1 开工前

1. `git pull` 后确认文件头「基准」的 hash 与 `git log -2 --format=%h -- plan/待办清单.md` 的**第二行**对得上；
   对不上说明有人改过没更新头，先对齐。
   （不要拿 `git log -1` 比：`-1` 取到的是本次更新自己的提交，指针永远差一格 —— 这是早期版本的坑。）
2. 只在 §1 索引里挑条目，不要在正文里翻 —— 索引是优先级视图，正文是模块视图。

### 4.2 收工前（提交前必做）

| 情形 | 动作 |
|---|---|
| 整条做完 | 状态改 `已完成`；验收标准逐条打勾；`完成记录` 写 `日期 · 版本号 · <commit>`；CHANGELOG 新版本段写一句「修复：…（TD-xxx）」 |
| 做了一半 | 状态改 `进行中`；在「现状」末尾追加「已完成 X，剩 Y」；**不要新开条目** |
| 发现新需求 | 先查 §7 来源登记表；没有登记才在对应模块末尾追加，ID 取该模块当前最大号 +1 |
| 发现某条已过时 | 状态改 `已完成`，「完成记录」写「已被 TD-xxx 覆盖」，不留悬空条目 |
| 用户拍板了某条 | 「待拍板」改成 `已定：…`，状态转 `待办`；同步删掉 §2 对应行 |
| 只改了文档 | 也要更新「最后更新」的 hash —— 这个字段是给下一个 agent 判断「条目还准不准」用的 |

### 4.3 硬规则

- **ID 永不复用**。做完的条目进 §5 归档，编号作废，新条目往后排。
- **一条待办只做一件事**。改动超过 5 个文件或跨两个模块，拆成两条。
- **不许无验收项**。「优化一下」「后续完善」这类不许进本文件。
- **不复制 CHANGELOG 全文**。来源只写 ID，正文只写「为什么 / 怎么做 / 怎么验」。
- **不写「定期回顾」**。回顾就发生在每次收工前的 4.2 表格里。

### 4.4 状态机

`待拍板` →（用户答复）→ `待办` → `进行中` → `已完成` → 归档。
唯一例外：`待办` 可直接跳 `已完成`（例如判定为「已被覆盖」）。

## 附：条目填写标准

| 字段 | 合格线 |
|---|---|
| 优先级 | P0 = 不做会阻塞发布或造成不可逆损失；P1 = 用户明确要或缺了不完整；P2 = 打磨。必须写得出一句理由 |
| 状态 | 只用 `待办` / `待拍板` / `进行中` / `已完成` |
| 来源 | 只写 §7 表里的 ID，不抄原文。找不到就先在 §7 建一行 |
| 为什么做 | 一到两句，说清「谁的什么问题」，不写技术方案 |
| 现状 | **必须带 `文件:行号`**，并标 `【核实】`/`【待复核】`。找不到就写「未找到（grep 关键词：…）」，禁止凭印象写 |
| 改动点 | 有序步骤，每步落到具体文件；跨 crate 写清边界；`sdk/` 一律写「不动」 |
| 验收标准 | `- [ ]` 复选；每条是命令或可观察行为；至少一条自动化（`cargo test` / `pnpm exec tsc --noEmit`），纯人工的写明「需真机」 |
| 依赖 / 风险 | 会被牵连的模块、业务铁律、不可逆操作；没有写「无」 |
| 待拍板 | 没有写「无」；有则必须给选项 + 建议默认 + 阻塞范围，否则状态不能是 `待办` |
| 完成记录 | 日期 · 版本号 · commit 短 hash。三样齐了才算完成 |
