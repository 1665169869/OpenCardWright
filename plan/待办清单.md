#### TD-101 管理卡模拟构包按卡型区分

**优先级** P1 · **状态** 待办 · **来源** ST-1, CL-0036-3 · **模块** 发卡与卡片

**为什么做**：模拟模式（`OCW_SIM=1`）下总控、复位、清除、校时卡回放的字节完全一样，演示时看起来「发什么卡都一样」，也没法用它验证读取侧的卡型分支。

**现状**【核实】：`opencardwright/src-tauri/src/state.rs:51` 的模拟分支只判断
`if args.contains(&"install")` → `INSTALL_JSON`，其余一律回放 `GUEST_DAY_JSON`；
`crates/ocw-device/src/sim.rs` 只有 `INSTALL_JSON` / `GUEST_DAY_JSON` 两个常量；
`tools/CardBuild.cs` 只支持客卡与安装卡。

**改动点**
1. `opencardwright/tools/CardBuild.cs`：加 `--type`（客卡 / 安装 / 总控 / 复位 / 清除 / 退房钟点 / 校时），调用 `CardBuilder` 对应分支。
2. `crates/ocw-device/src/sim.rs`：加 `AdminSpec` + `issue_admin()`，保留「缺构包器时退回固定样本」的兜底。
3. `src-tauri/src/state.rs`：删掉 install / 其余的二元回放，改为委托 `issue_admin()`；拿不到类型就报错，不要静默回放客卡。
4. `crates/ocw-device/tests/sim_cardbuild.rs`：补断言。

**验收标准**
- [ ] 模拟模式下依次发六类管理卡，`raw_hex` 两两不同
- [ ] 每类字节与 `PMSLockCard.exe selftest` 中同名向量一致（以 `docs/抓包样本与验证记录.md` 为准，不要自己编期望值）
- [ ] `cargo test -p ocw-device --test sim_cardbuild` 通过，新增至少 3 条断言
- [ ] 未改 `sdk/`

**依赖 / 风险**：`CardBuild.cs` 在 `opencardwright/tools/`，可改；`sdk/*.cs` **不可改**（AGENTS §0/§9）。

**待拍板**：无

**验收标准**
- [ ] 进入管理卡页，卡型下拉显示「总控卡」
- [ ] 其余默认值不变
- [ ] `npx tsc --noEmit` 通过

**依赖 / 风险**：无（纯前端默认值）。

#### TD-103 发卡页预计退房改 TimePicker

**优先级** P2 · **状态** 待办 · **来源** ST-5 · **模块** 发卡与卡片

**为什么做**：现在退房时间固定按「入住 + N 天的中午 12:00」推算，前台没法表达「客人要求 14:00 退房」。

**现状**【核实】：`opencardwright/src/components/IssueForm.tsx:57` 注释写死「日租按入住当天 + N 天的中午 12:00」，
`:143` 渲染 `预计退房：{startAt} - {checkoutAt}`，`:146` 已有说明「按发卡时间估算……门锁实际从首次刷卡起算」。无任何时间选择控件。

**改动点**
1. 日租增加「预计退房时间」`TimePicker`（默认 12:00），据此换算生效天数。
2. 换算结果仍受 `src-tauri/src/rules.rs` 与 `src/api.ts` 的档位表约束（≥ 1 天、≤ 62 天）。
3. 钟点卡不动。

**验收标准**
- [ ] 选 14:00 后展示区间随之变化，跨零点能算出正确天数
- [ ] 写卡仍是「天数」，卡内字节不因时分变化
- [ ] 62 天上限仍被拦截
- [ ] 界面上保留一行说明「时间只影响记录与到期估算，锁按首次刷卡起算」

**依赖 / 风险**：最后一条是**必须**的 —— 卡里只有时长码、没有绝对到期时刻（`opencardwright/README.md` §6 第 7 条），不写清会变成售后纠纷。

#### TD-104 长有效期卡（1095 天）发卡前确认词

**优先级** P1 · **状态** 待办 · **来源** P8 · **模块** 发卡与卡片

**为什么做**：方案 §8 要求 1095 天卡「需输确认词，写明会把该房间有效卡顶到 3 年后」。现在只有一句
`长有效期卡会顶高该房间的水位` 的提示条（`src/components/IssueForm.tsx`），点一下就能发 —— 而**刷一次门就会把该房高水位顶到三年后**，
之后正常卡全废、只能用复位卡恢复（`AGENTS.md` §6）。

**现状**【核实】：`IssueForm` / `AdminCards` 均无确认词输入；`dayOptions` 里 90/120/…/1095 天档位可直接选中即发。

**改动点**
1. 前端：选中档位 > 63 天（`0xC0` 月码段）时，在发卡按钮旁要求输入固定确认词（如「顶高水位」），
   不填/填错保持按钮禁用，并在弹窗里列出该房当前有效卡与发卡后的预计水位。
2. 后端兜底：`issue_guest_card` / `issue_admin_card` 接收 `confirmLong: Option<String>`，
   档位进入月码段且确认词不符时返回 4xx（不信任前端）。
3. 审计详情里带上「长有效期卡确认词已输入」。

**验收标准**
- [ ] 选 1095 天不发确认词 → 按钮禁用或后端拒绝，库里无记录
- [ ] 输入正确确认词 → 正常发卡，审计可查
- [ ] 63 天以内不受影响（不需要确认词）

**依赖 / 风险**：确认词文案要写清后果，且**不能**把复位卡的恢复方法省略。
**待拍板**：确认词具体用哪几个字（建议「顶高水位」；也可让 admin 在设置里自定义）。
**完成记录**：—

### C. 提醒与通知

#### TD-301 到期提醒「温柔女声播报」

**优先级** P2 · **状态** 待拍板 · **来源** ST-2 · **模块** 提醒与通知

**为什么做**：前台忙的时候不一定看屏幕，现在的提示音只是两声蜂鸣，不传达「哪间房、还剩多久」。

**现状**【核实】：`src/utils/sound.ts` 用 Web Audio 合成提示音，`playAlert()` 可用；
`src/components/ExpiryBell.tsx` 只做列表展示；到期数据来自 `expiring_cards` 命令 + App 内轮询；
登录时已调用解锁音频上下文的逻辑（执行时在 `AuthGate.tsx` 核对函数名）。全仓无 `speechSynthesis`。

**改动点（按 Q-301 选 A 时）**
1. `sound.ts` 加 `speak(text)`：`speechSynthesis` + `zh-CN`，语速放慢（约 0.9）。
2. 文本模板：「220 房还有 2 小时到期，请提醒。」不足 1 小时按分钟说。
3. App 轮询拿到新到期项时调用；**同一张卡只播一次**（按 `card_no` + 到期时间做窗口去重，避免轮询重复播）。
4. 设置 → 到期提醒 增加「语音播报」开关（复用现有 reminder 设置项，不新建表）。
5. 无中文语音或合成失败时静默回退 `playAlert()`，不弹错。

**验收标准**
- [ ] 到期项首次出现时播报一次，后续轮询不重复
- [ ] 关闭开关后只保留提示音
- [ ] 系统无中文语音包时不报错，仍有提示音
- [ ] 设置页有开关且持久化

**依赖 / 风险**：WebView2 的语音依赖系统 TTS，「温柔」无法保证，条目与设置项文案都要写「音色随系统」。

## 4. 维护约定（每轮照做）

### 4.1 开工前

1. `git pull` 后确认文件头「最后更新」的 hash 与 `git log -1 --format=%h` 对得上；对不上说明有人改过没更新头，先对齐。
2. 只在 §1 索引里挑条目，不要在正文里翻 —— 索引是优先级视图，正文是模块视图。

### 4.2 收工前（提交前必做）

| 情形 | 动作 |
|---|---|
| 整条做完 | 状态改 `已完成`；验收标准逐条打勾；`完成记录` 写 `日期 · 版本号 · <commit>`；CHANGELOG 新版本段写一句「修复：…（TD-xxx）」 |
| 做了一半 | 状态改 `进行中`；在「现状」末尾追加「已完成 X，剩 Y」；**不要新开条目** |
| 发现新需求 | 先查 §7 来源登记表；没有登记才在对应模块末尾追加，ID 取该模块当前最大号 +1 |
| 发现某条已过时 | 状态改 `已完成`，「完成记录」写「已被 TD-xxx 覆盖」，不留悬空条目 |
| 用户拍板了某条 | 「待拍板」改成 `已定：…`，状态转 `待办`；同步删掉 §2 对应行 |
| 只改了文档 | 也要更新「最后更新」的 hash —— 这个字段是给下一个 agent 判断「条目还准不准」用的 |

### 4.3 硬规则

- **ID 永不复用**。做完的条目进 §5 归档，编号作废，新条目往后排。
- **一条待办只做一件事**。改动超过 5 个文件或跨两个模块，拆成两条。
- **不许无验收项**。「优化一下」「后续完善」这类不许进本文件。
- **不复制 CHANGELOG 全文**。来源只写 ID，正文只写「为什么 / 怎么做 / 怎么验」。
- **不写「定期回顾」**。回顾就发生在每次收工前的 4.2 表格里。

### 4.4 状态机

`待拍板` →（用户答复）→ `待办` → `进行中` → `已完成` → 归档。
唯一例外：`待办` 可直接跳 `已完成`（例如判定为「已被覆盖」）。

## 附：条目填写标准

| 字段 | 合格线 |
|---|---|
| 优先级 | P0 = 不做会阻塞发布或造成不可逆损失；P1 = 用户明确要或缺了不完整；P2 = 打磨。必须写得出一句理由 |
| 状态 | 只用 `待办` / `待拍板` / `进行中` / `已完成` |
| 来源 | 只写 §7 表里的 ID，不抄原文。找不到就先在 §7 建一行 |
| 为什么做 | 一到两句，说清「谁的什么问题」，不写技术方案 |
| 现状 | **必须带 `文件:行号`**，并标 `【核实】`/`【待复核】`。找不到就写「未找到（grep 关键词：…）」，禁止凭印象写 |
| 改动点 | 有序步骤，每步落到具体文件；跨 crate 写清边界；`sdk/` 一律写「不动」 |
| 验收标准 | `- [ ]` 复选；每条是命令或可观察行为；至少一条自动化（`cargo test` / `npx tsc --noEmit`），纯人工的写明「需真机」 |
| 依赖 / 风险 | 会被牵连的模块、业务铁律、不可逆操作；没有写「无」 |
| 待拍板 | 没有写「无」；有则必须给选项 + 建议默认 + 阻塞范围，否则状态不能是 `待办` |
| 完成记录 | 日期 · 版本号 · commit 短 hash。三样齐了才算完成 |
