#### TD-105 校时卡后验证 1 小时钟点客卡按时失效

**优先级** P1 · **状态** 已完成 · **来源** US-1106-1 · **模块** 发卡与卡片

**为什么做**：钟点客卡（`GuestHour`）在锁上是否按小时失效一直没定论。此前实测「1 小时卡发卡 65 分钟后首刷能开；首刷后 3 小时 22 分复刷仍能开」，推测锁内缺时间基准；若刷校时卡后仍不失效，说明到期判定还有别的条件，产品的钟点卡到期提示就不能当作锁行为。

**现状**【核实】：
- `docs/TEMIC门锁卡技术规格.md` §11.1 记录上述实测，并给出未执行的验证步骤「刷校时卡 → 发 1 小时卡 → 首刷 → 等 1 小时 → 复刷」。
- 校时卡编码已解：`sdk/PMSLockSDK.cs:285` 注释「值 = 16 × 当日分钟数 + 953，只含当日时/分，不含日期」；技术规格 §9 有四点命中记录。
- 1 小时钟点客卡：`sdk/PMSLockSDK.cs:210` `BuildGuestHour`，页2 为 `0x40 | (小时 + 1)`，1 小时即 `0x42`。
- 锁内到期判定与校时卡的关系为【待定】；本仓库没有锁固件代码，只能实测。

**改动点（验证步骤，无代码改动）**
1. 用**测试锁 / 空房**，确认该房当日没有正常客卡；准备一张校时卡（原厂或本 SDK 生成，字节一致）和一张 1 小时钟点客卡。
2. 先刷校时卡，记录其 28 字节、刷卡时刻与锁的反应。
3. 立即发 1 小时钟点客卡并**首刷开门**（首刷才是计时起点），记录发卡时刻、首刷时刻、`CardNo`、卡内 8 字节。
4. 从**首刷时刻**起等待 65 分钟（>60 分钟，避开边界误差），再次刷卡。
5. 记录复刷结果（开 / 拒）与锁的提示（灯 / 声 / 蜂鸣次数）；若仍能开，延长到 3 小时再复刷一次，区分「完全不会过期」与「计时不准」。
6. 换一把未刷过校时卡的测试锁做对照（或不刷校时卡重复步骤 3–4），确认差异是否来自校时卡。

## 4. 维护约定（每轮照做）

### 4.1 开工前

1. `git pull` 后确认文件头「基准」的 hash 与 `git log -2 --format=%h -- plan/待办清单.md` 的**第二行**对得上；
   对不上说明有人改过没更新头，先对齐。
   （不要拿 `git log -1` 比：`-1` 取到的是本次更新自己的提交，指针永远差一格 —— 这是早期版本的坑。）
2. 只在 §1 索引里挑条目，不要在正文里翻 —— 索引是优先级视图，正文是模块视图。

### 4.2 收工前（提交前必做）

| 情形 | 动作 |
|---|---|
| 整条做完 | 状态改 `已完成`；验收标准逐条打勾；`完成记录` 写 `日期 · 版本号 · <commit>`；CHANGELOG 新版本段写一句「修复：…（TD-xxx）」 |
| 做了一半 | 状态改 `进行中`；在「现状」末尾追加「已完成 X，剩 Y」；**不要新开条目** |
| 发现新需求 | 先查 §7 来源登记表；没有登记才在对应模块末尾追加，ID 取该模块当前最大号 +1 |
| 发现某条已过时 | 状态改 `已完成`，「完成记录」写「已被 TD-xxx 覆盖」，不留悬空条目 |
| 用户拍板了某条 | 「待拍板」改成 `已定：…`，状态转 `待办`；同步删掉 §2 对应行 |
| 只改了文档 | 也要更新「最后更新」的 hash —— 这个字段是给下一个 agent 判断「条目还准不准」用的 |

### 4.3 硬规则

- **ID 永不复用**。做完的条目进 §5 归档，编号作废，新条目往后排。
- **一条待办只做一件事**。改动超过 5 个文件或跨两个模块，拆成两条。
- **不许无验收项**。「优化一下」「后续完善」这类不许进本文件。
- **不复制 CHANGELOG 全文**。来源只写 ID，正文只写「为什么 / 怎么做 / 怎么验」。
- **不写「定期回顾」**。回顾就发生在每次收工前的 4.2 表格里。

### 4.4 状态机

`待拍板` →（用户答复）→ `待办` → `进行中` → `已完成` → 归档。
唯一例外：`待办` 可直接跳 `已完成`（例如判定为「已被覆盖」）。

## 附：条目填写标准

| 字段 | 合格线 |
|---|---|
| 优先级 | P0 = 不做会阻塞发布或造成不可逆损失；P1 = 用户明确要或缺了不完整；P2 = 打磨。必须写得出一句理由 |
| 状态 | 只用 `待办` / `待拍板` / `进行中` / `已完成` |
| 来源 | 只写 §7 表里的 ID，不抄原文。找不到就先在 §7 建一行 |
| 为什么做 | 一到两句，说清「谁的什么问题」，不写技术方案 |
| 现状 | **必须带 `文件:行号`**，并标 `【核实】`/`【待复核】`。找不到就写「未找到（grep 关键词：…）」，禁止凭印象写 |
| 改动点 | 有序步骤，每步落到具体文件；跨 crate 写清边界；`sdk/` 一律写「不动」 |
| 验收标准 | `- [ ]` 复选；每条是命令或可观察行为；至少一条自动化（`cargo test` / `npx tsc --noEmit`），纯人工的写明「需真机」 |
| 依赖 / 风险 | 会被牵连的模块、业务铁律、不可逆操作；没有写「无」 |
| 待拍板 | 没有写「无」；有则必须给选项 + 建议默认 + 阻塞范围，否则状态不能是 `待办` |
| 完成记录 | 日期 · 版本号 · commit 短 hash。三样齐了才算完成 |
